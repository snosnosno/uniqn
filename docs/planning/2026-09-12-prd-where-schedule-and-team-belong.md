# 근무표와 팀은 PRD 어디에 녹아야 하는가

- 작성일: 2026-09-12
- 질문: "앱 전체의 PRD는 공고 작성해서 지원받고 확정해서 출퇴근하고 정산까지인데, 근무표와 팀은 어떻게 녹아야 하나"
- 선행: [관계·중복 분석](2026-09-12-schedule-team-posting-ia-analysis.md) · [워크플로우 분석](2026-09-12-employer-workflow-ux-analysis.md)

## 0. 결론 먼저

**근무표는 파이프라인에 "녹이는" 게 아니라, 파이프라인을 담는 그릇으로 올려야 한다.
팀은 화면에서 빼고 범위(scope)로만 남긴다.**

그리고 질문의 전제를 하나 고쳐야 한다 —
**`공고 → 지원 → 확정 → 출퇴근 → 정산`은 이 앱의 파이프라인 전체가 아니라 셋 중 하나다.**

---

## 1. 실측 — 출퇴근·정산에 도달하는 길이 셋이다

| | 경로 | 출퇴근 | 정산 | 근거 |
|---|---|---|---|---|
| ① | **dated 공고** → 지원 → 확정 → 출퇴근 → 정산 | ✅ | ✅ | PRD가 기술하는 유일한 길 |
| ② | **근무표 직접 배치** → 출퇴근 → 정산 | ✅ | ✅ | 공고를 아예 거치지 않는다 (`add_direct_staff`) |
| ③ | **fixed 공고**(상시 모집) → 지원 → 확정 → **끝** | ❌ | ❌ | QR 진입점 자체가 차단 (`[id]/_layout.tsx:30`) |

③의 근거는 코드에 명시돼 있다 — `isFixed` 는 **"QR 진입점 차단용"**이고(`_layout.tsx:30`),
공고 상세는 fixed 일 때 취소요청·노쇼·정산 카운트를 전부 0 으로 눌러 둔다(`index.tsx:608-611`).
근무표 파생 좌석도 `dated only` 다(`buildGridCells.ts:20`).

**즉 PRD 한 줄은 ① 하나만 설명한다.** 그런데 앱의 정보구조가 그 한 문장을 그대로 골격으로 삼아서,
②(홀덤펍 사장의 일상)는 "버튼 하나 뒤"로 밀렸고 ③(상시 모집)은 반쪽으로 남았다.

### 공통 분모는 공고가 아니라 `work_log` 다

세 길 모두 끝에 똑같은 한 줄을 만든다 — **"어느 지점, 어느 날짜, 누가, 몇 시부터"**.
그 줄들의 집합이 근무표다. 공고는 그 줄을 만드는 **세 가지 방법 중 하나**일 뿐이다.

> 🔍 이름이 이미 진실을 알고 있다: 출퇴근 QR 페이로드의 타입은 `'venue'` 인데
> 실제로 담기는 값은 `jobPostingId` 다(`eventQRService.ts:175`). 코드가 지점 단위를 원하면서
> 공고 단위로 구현돼 있다는 흔적이다.

## 2. 그래서 PRD 한 줄을 이렇게 고친다

```
기존:  공고 작성 → 지원 → 확정 → 출퇴근 → 정산

제안:  날짜별 필요 인원
         → [ 아는 사람은 바로 배치 │ 모르는 사람은 공고로 모집 ]
         → 근무 확정 → 출퇴근 → 정산
```

여기서 **공고는 접속사 하나로 줄어든다.** 그게 정확한 비중이다.

제품 기준선은 이미 같은 말을 하고 있다 —
> §2-1: "근무표가 내부 운영 계획의 정본이고 공고는 부족 인원을 모집하는 공개 문서다."

**문서는 맞게 썼는데 화면이 못 따라갔다.** 이 분석의 대부분은 새 발명이 아니라 그 격차의 목록이다.

### 비유

근무표는 **예약 장부**, 공고는 **빈 자리 광고**다.
광고가 장부의 한 줄을 만들 수는 있지만, 장부가 광고에서 파생되지는 않는다.
지금 앱은 장부를 광고의 부속품처럼 취급한다 — 탭 이름이 "내 공고"이고 근무표는 그 안의 버튼이다.

---

## 3. 근무표가 녹는 방식 — 기능이 아니라 "상태를 가진 셀"

근무표 셀 하나 = `work_log` 하나 = **파이프라인 5단계의 수명주기 그 자체**.

```
빈 셀 ──→ 배치됨 ──→ 출근 ──→ 퇴근 ──→ 정산 대기 ──→ 지급 완료
 │         ↑       scheduled  checked_in  checked_out
 │         │
 │         ├─ ② 직접 배치 (아는 사람 — 공고 없음)
 │         └─ ① 공고 확정 (모르는 사람)
 │
 └─ 필요 인원만 정해진 상태 = 부족 → 공고 트리거
```

이렇게 보면 근무표는 **새 기능이 아니라 기존 5단계를 날짜 축으로 눕힌 뷰**다.
질문을 다시 쓰면: "어떻게 녹이나"가 아니라 **"이미 녹아 있는데 화면이 왜 안 보여주나"**.

### 셀이 해야 할 일과 현재 상태

| 셀 상태 | 필요한 행동 | 현재 |
|---|---|---|
| 부족 | 공고 만들기 | ✅ 있음 (`부족 N명 공고로 모집`) |
| 배치됨 | 누가·어느 역할·몇 시 | ✅ 있음 |
| 출근/퇴근 | QR · 수동 정정 | ✅ 있음 (통합 시트 1개로 수렴, #424) |
| 정산 | 얼마 | ⚠️ 있지만 **다른 화면**(공고 정산 / 지점 정산 2개) |
| 출처 | **어느 공고에서 왔나** | ❌ 없음 — 근무표→공고는 `create` 뿐 |

마지막 하나가 빠져서 "공고는 셀을 채우는 도구"라는 관계가 **화면상으로 성립하지 않는다.**
셀에 출처 공고 칩 하나만 달아도 두 개념의 주종이 눈에 보인다.

---

## 4. 팀이 녹는 방식 — 기능이 아니라 필터

**팀은 파이프라인 위에 있지 않다. 파이프라인 전체에 걸린 권한 경계다.**
그래서 "어디에 녹이나"가 아니라 **"화면을 가질 자격이 있나"**를 물어야 한다.

지금 팀 화면이 하는 일: 이름 변경 / 멤버 초대·제거 / 보관 / **근무표 링크**.
앞의 셋은 설정이고, 마지막 하나는 팀이 자기 존재 이유를 못 찾아서 얻어 단 것이다.
코드 주석이 그대로 고백한다 —

> `workspace/index.tsx:269` — *"근무표는 팀에 속한 지점의 일정인데 정작 팀에서 근무표로 가는 링크가 없었다."*

### 제안

| 상황 | 팀을 어떻게 |
|---|---|
| 멤버 1명 (홀덤펍 사장 대부분) | **아예 노출하지 않는다.** 지금은 자동 생성된 빈 껍데기가 ⋯ 메뉴 한 칸을 차지한다 |
| 멤버 2명 이상 | `WorkspaceContextBar` 한 줄이면 충분하다 — **이미 만들어져 있고 2개 화면에서 쓰고 있다** |
| 멤버 관리 | 설정 하위로 내린다 |

그리고 공고 협업자와의 관계를 한 줄로 못박는다:
**"팀 = 모든 공고를 함께 / 협업자 = 이 공고만 함께"**
지금은 이름이 둘 다 "함께 관리하는 사람"이라 어느 쪽을 쓸지 판단할 근거가 화면에 없다.

## 5. (묻지 않았지만) 지점이 혼란의 진짜 뿌리다

컨테이너 개념이 **셋**이다: 팀(workspace) / 지점(venue) / 공고(posting).
그런데 지점은 별도 테이블이 아니라 `job_postings` 의 `status='container'` 행이다.

| | 팀 | 지점 | |
|---|---|---|---|
| 홀덤펍 사장 | 내 가게 | 내 가게 | ← **같은 것을 두 겹으로 모델링** |
| 대회사 | 회사 | 대회 현장 여러 곳 | ← 두 겹이 제 값을 한다 |

**지점이 값을 하는 건 대회사뿐이다.** 홀덤펍에겐 순수 오버헤드고, 실제로 팀과 지점 이름이
겹쳐 사고가 난 이력도 있다(`work-schedule.tsx:122` 주석, S1).

> 제안: 지점이 1개면 선택기를 숨긴다. 2개 이상일 때만 1급 개념으로 올린다.
> 홀덤펍 사장은 "팀"도 "지점"도 모른 채 근무표만 쓰면 된다.

## 6. 한 장 그림

```
 ┌────────── 팀 (권한 범위 — 화면 아님, 멤버 2명+ 일 때만 컨텍스트 한 줄) ──────────┐
 │                                                                                │
 │  ┌───────── 지점 (물리적 운영 단위 — 2개 이상일 때만 노출) ─────────────────┐   │
 │  │                                                                        │   │
 │  │   ███  근무표 = 날짜 × 사람 격자   ←← 운영의 홈  ███                    │   │
 │  │                                                                        │   │
 │  │   셀 수명:  부족 ─→ 배치 ─→ 출근 ─→ 퇴근 ─→ 정산                        │   │
 │  │              │                                                         │   │
 │  │              ├─ ② 아는 사람   → 직접 배치 (공고 없음)                   │   │
 │  │              └─ ① 모르는 사람 → 공고 → 지원 → 확정 ──┐                  │   │
 │  │                                                      └→ 같은 셀로 합류  │   │
 │  └────────────────────────────────────────────────────────────────────────┘   │
 └────────────────────────────────────────────────────────────────────────────────┘

 ③ fixed 공고(상시 모집)는 이 격자 밖에 있다 — 날짜가 없어서.
    역할은 "풀 만들기"이고, 만들어진 풀은 ② 직접 배치로 격자에 들어온다.
```

③이 격자 밖인 건 **결함이 아니라 올바른 설계**다. 다만 지금은 그 사실이 사용자에게
설명되지 않아서, 상시 공고를 올린 사장이 "왜 출퇴근 QR이 없지?"에서 막힌다.

> 제안: fixed 공고 상세에 한 줄 — *"상시 공고는 사람을 모으는 용도예요. 실제 근무일은 근무표에서 배치하세요."* + 근무표 링크.

## 7. 로드맵 (기존 우선순위와 접붙임)

| Phase | 내용 | 이 문서와의 관계 | 상태 |
|---|---|---|---|
| 0 | P0 2건 — 계획값 오염 · 무음 유실 차단 | 격자의 숫자를 믿을 수 있게 | ✅ PR #490 |
| 1 | **"오늘" 화면** | 근무표를 날짜 축 홈으로 세우는 첫 걸음. 새 데이터 0 | 미착수 |
| 2 | 근무표 ↔ 공고 양방향 + **셀에 출처 공고 표시** | "공고는 셀을 채우는 도구"가 화면으로 성립 | 미착수 |
| 3 | 정산을 지점 월 단위 하나로 | 셀의 종착 상태가 한 곳에 모임 | 미착수 |
| 4 | 팀·지점 계층 **조건부 노출** | 1인 사장에게 개념 2개 제거 | 미착수 |
| 5 | fixed 공고에 "풀 만들기" 설명 + 근무표 링크 | ③의 역할을 명시 | 미착수 |
| 6 | 탭 재정의 (운영 / 정산 / 설정) | 판단 필요 — 실기기 QA 동반 웨이브 | 보류 |

Phase 1~2 만으로도 "근무표가 그릇"이라는 관계가 화면에서 성립한다. 탭 구조를 안 건드려도 된다.

## 8. 반론 — 공고를 낮추면 안 되는 이유도 있다

공고는 **이 앱의 유일한 외부 접점**이다.
구직자가 보는 건 공고뿐이고, 신규 사용자 획득도 공고 공유에서 온다.

그래서 사장 화면에서 공고의 **위상**을 낮추더라도,
공유 · 지원 QR · 구직자 시선 미리보기 같은 **유통 기능은 오히려 더 눈에 띄어야 한다.**

> 근무표를 홈으로 올리는 것과 공고 유통을 약화시키는 것은 다른 얘기다.
> Phase 2에서 셀에 공고 칩을 달 때, 그 칩이 공유 CTA 로도 이어지면 둘을 동시에 만족시킨다.
