## 2. 주문서 구성

유형은 최상단 **세그먼트 버튼**(지원|급구|고정|대회)으로 가장 먼저 선택. 고정·대회 선택 시 기존 상세 폼으로 전환. 이하 행 그룹은 현행 폼 섹션 순서 그대로:

```
[프리셋 카드 캐러셀: ⚡마지막 공고 · 저장 템플릿들 · +저장]
[유형 세그먼트: 지원 | 급구 | 고정 | 대회]
── 기본 정보 ──   제목 · 장소 · 연락처 · 설명
── 일정 · 모집 ──  날짜 · 시간 · 역할
── 급여 ──        급여 · 복지 · 세금
── 조건 ──        조건 (복장·경력)          ← 신규 항목
── 사전질문 ──    사전질문
[ 이대로 등록 ]
```

- 필수 항목 미입력 시 행에 **미설정** 배지. 등록 버튼이 첫 미설정 항목의 시트를 순차로 열어 유도(첫 작성자 온보딩). 첫 미설정은 제목 → "제목부터 입력하기".
- 첫 등록 완료 시 "이 구성을 프리셋으로 저장할까요?" 제안.
- 주간그리드 프리필(venueId/date/count 파라미터)은 주문서가 흡수 — 기존 동선 무회귀.

## 3. 시트 12종 스펙

| 시트 | 성격 | 내용 |
|---|---|---|
| 제목 | 신규 | 직접 입력(25자) + "프리셋 제목 사용"·최근 제목 칩. **자동 조합 없음** |
| 장소 | 신규 | 최근 사용 장소 리스트에서 탭 선택 + "새 장소 입력"(장소명/주소, 지역 자동 제안) |
| 연락처 | 신규 | 프로필 번호 기본 선택 + 다른 번호 입력 |
| 설명 | 신규 | 멀티라인(500자), 선택 — 비워도 등록 가능 |
| 날짜 | 기존 재사용 | DatePickerModal — **달력만**, 퀵칩 등 부가 요소 없음. 멀티 선택(지원 최대 7일 등 타입별 제약 유지) |
| 시간 | 기존 재사용 | **출근시간만** 설정(TimeWheelPicker 시/분). **시간대 여러 개 추가 가능** — 시간대마다 역할 배정(현행 dated requirements 구조 그대로) |
| 역할 | 기존 재사용 | 6종 칩 + **기타=직접 입력**. 역할별 인원 스테퍼(±1명) + "＋ 이 역할 추가"로 **다역할** 지원 |
| 급여 | 신규 | 세그먼트 **시급\|일급\|월급**. 기본값에서 ±1,000원 스테퍼 + 직접 입력. 기본값: **시급 20,000 · 일급 200,000 · 월급 2,500,000**. "모든 역할 동일 급여" 토글 유지 |
| 복지 | 기존 에디터 확장 | **식사 · 교통 · 보장시간 · 숙소** — 항목별 체크 또는 금액 입력 |
| 세금 | 기존 에디터 래핑 | 원천징수 3.3%(기본) / 세금 없음 / 직접 설정 |
| 조건 | **신규 항목** | **복장**: 검정셔츠/슬랙스 · 흰셔츠/슬랙스 · 직접 입력 / **경력**: TDA 숙지자 · 6개월 이상 · 직접 입력 |
| 사전질문 | 기존 에디터 래핑 | 토글 + 질문 목록(단답/장문/선택형, 최대 10개) |

시트 공통: SheetModal/embedded 패턴(중첩 RN Modal iOS 터치먹통 함정 회피), `dark:` 토큰, 큰 터치 타깃.

## 4. 아키텍처 — "스키마는 새로, 모양은 호환"

```
주문서 UI (RHF + zodResolver)
  → zod 스키마 + 매퍼 (XSS refine · #194 own-property 가드 승계)
  → useCreateJobPosting (기존 훅)
  → jobManagementService → JobPostingRepository.createWithTransaction (기존, RLS 무변경)
```

- **zod 스키마**(`src/schemas/jobPosting/`): 기존 canonical `JobPostingDraft` 모양을 그대로 계약으로 승격. `jobPostingDraftSchema`(XSS refine 전 텍스트 필드), `templateDataSchema`(normalize 선행 흡수 후 safeParse — #146 교훈).
- **RHF**: `useForm<OrderSheetValues>`(주문서 행 1:1 평탄 구조, zod 추론). 행 단위 에러 배지.
- **매퍼**(작은 파일 분리): `valuesToDraft` / `draftToValues` / `templateToValues` / `gridParamsToValues` / `valuesToCreateInput`. own-property 가드 패턴(#194 region 유실 재발 방지) + 고정 회귀 테스트.
- **draftAdapter는 이번에 삭제하지 않음** — 고정·대회 폼과 edit이 계속 사용. 템플릿 직렬화 포맷 동일 유지 → 신·구 상호 호환, **템플릿 마이그레이션 불필요**.
- 신규 의존성 0 (zod 4·react-hook-form 7.68·resolvers 기설치 확인).
- JS-only → OTA 출하 가능.

### 신규 데이터 필드 (서버 확인 필요 — 유일한 스키마 접점)
- **조건**: 복장(dressCode) · 경력(experience) — 프리셋 값 or 자유 텍스트.
- **복지 금액**: 식사/교통/보장시간/숙소 각 항목의 체크 + 선택적 금액.
- 구현 계획 단계에서 `job_postings` 기존 JSONB(requirements/compensation 계열) 수용 가능 여부 실측 → 가능하면 무마이그레이션, 불가하면 최소 컬럼/키 추가. 기존 급여타입 "기타(other)"로 저장된 공고는 **읽기 호환 유지**(표시만, 신규 작성은 시급/일급/월급).

## 5. 검증·테스트 전략

- zod 스키마 단위 테스트(XSS·경계값·NULL 흡수).
- 레거시 템플릿 픽스처 파싱(구버전 draft 스냅샷 → normalize → 통과).
- own-property 가드 red-green(#194 재현 → 수정 확인).
- 신·구 동등성: 같은 입력 의도 → `valuesToCreateInput` 결과 == 기존 `buildCreateJobPostingInput` 결과.
- 키오스크 플로우 e2e 1본(프리셋 → 수정 → 등록 → 완료 화면).
- edit 화면 코드 무변경 — 기존 테스트 커버 유지 확인.

## 6. 이번에 안 하는 것 (슬라이스 경계)

- 고정·대회 타입 키오스크화(기존 상세 폼 유지) / edit 이관 / draftAdapter 삭제(이관 완료 후)
- 위저드 3스텝(D안) — 첫 작성자 이탈 데이터 확인 후 주문서 앞에 얹는 후속 진화
- 로컬 임시저장(기존 제외 결정 유지)
- 서버 스키마·RLS 변경 — §4의 조건·복지 필드 수용 확인 외 없음

## 7. 후속 백로그

- D안 진화: 프리셋 없으면 위저드 3스텝(날짜→역할·인원→시간) → 주문서 착륙
- 고정·대회 주문서화 + edit 이관 → draftAdapter 제거(재구축 완결)
- create/edit 폼 마크업 중복 해소(edit 이관과 동일 슬라이스)
