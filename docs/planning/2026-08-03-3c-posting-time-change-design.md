## 0. 한 줄 결론

**3-C 는 새 기능이 아니라 기존 단건 편집(`update_work_log_slot`)의 "묶음 적용"이다.** 알림·취소·동기화 배선은 이미 전부 존재하므로, 새로 만들 것은 **묶음을 고르는 축(슬롯 키)** 과 **N건을 한 트랜잭션으로 도는 RPC** 뿐이다.

## 1. 사용자 결정 (2026-08-03 확정 — 설계의 전제)

| # | 질문 | 결정 | 설계 귀결 |
|---|---|---|---|
| 1 | 확정 스태프 시간 일괄 변경에 동의가 필요한가 | **불필요.** 알림·동기화만 정확하면 된다 | pending/승인 상태 **만들지 않는다**. 변경은 단일 트랜잭션으로 즉시 확정 |
| 2 | 스태프가 거절하면 그 자리는 | **기존 취소요청 경로**를 탄다 | 신규 "거절" 상태 **없음**. 공석 처리는 이미 있는 `cancellation_request` 흐름이 담당 |
| 3 | 개인 조정 vs 전체 변경 충돌 | **전체가 이긴다(덮어쓰기)** | 개별 조정 보존 로직 **없음**. 대신 덮어쓴 사실이 알림에 실려야 한다 |

세 결정 모두 **"신규 상태 머신 없이 기존 경로 재사용"** 으로 수렴한다. 이것이 이 설계의 성격을 결정한다.

## 2. 범위

**전체 축** — 구인자가 공고의 한 슬롯(날짜 + 역할 + 시각)에 확정된 **모든** 스태프의 출근 예정 시각을 한 번에 바꾼다. (신규)

**개인 축** — 특정 스태프 1명의 시각만 바꾼다. **이미 있다** — `update_work_log_slot`(#407). 3-C 에서 새로 만들지 않는다.

범위 밖: 종료 시각(도메인상 예정 퇴근 시각이 없다 — [시간모델] 참조) · 역할 변경 · 날짜 이동.

## 3. 🔑 이미 있는 것 (이 설계의 절반은 "만들지 않기"다)

착수 전에 반드시 확인할 것 — 아래는 **전부 실측으로 확인된 기존 배선**이다. 다시 만들면 중복이 된다.

### 3-1. 알림은 이미 나간다

`notify_on_work_log_update()` **Case 2-B**(`20260731140000`, #382)가 `OLD.time_slot IS DISTINCT FROM NEW.time_slot` 을 직접 감지해 `schedule_change` 알림을 발행한다. 이력 배열을 경유하지 않으므로 **어떤 경로가 time_slot 을 바꾸든 자동으로 커버된다.**

- 수신자는 `NEW.staff_id` — 일괄 변경으로 N행이 바뀌면 **각자 자기 것 1건**을 받는다. 알림 폭풍이 아니라 정확한 개별 통지다.
- 본문에 `이전 → 이후` 라벨이 이미 들어간다. 미정 센티널도 '미정'·'협의' 로 번역된다.
- **SECDEF 는 트리거를 우회하지 않는다.** RPC 안에서 UPDATE 해도 발화한다(#407 주석 46-47행 실측).

🔑 **따라서 3-C 는 알림 코드를 한 줄도 쓰지 않는다.** 사용자 결정 1("알림만 잘하면 돼")은 UPDATE 를 올바르게 하는 것만으로 충족된다.

### 3-2. 취소 경로도 이미 배선돼 있다

같은 트리거의 `v_cancel_hint` 가 **"어려우시면 취소를 요청할 수 있어요"** 를 붙인다. 조건은 `application_id IS NOT NULL AND status = 'scheduled'` 로, 실제로 취소 버튼이 있는 사람에게만 말한다(`ScheduleDetailModal.tsx` 의 버튼이 `applicationId` 로 게이트되기 때문).

🔑 사용자 결정 2 는 **이미 구현돼 있다.** 3-C 가 할 일은 이 조건을 깨뜨리지 않는 것뿐이다.

### 3-3. 단건 동기화 로직도 이미 있다

`update_work_log_slot`(#407)이 `work_logs` + `applications.assignments` 를 한 트랜잭션으로 맞춘다. 특히 어려운 부분이 이미 풀려 있다:

- **셀 단위 분해** — 한 assignment 원소가 `dates:[d1,d2,d3]` 를 덮을 때 d2 만 편집하면 원소를 셋으로 쪼개고 나머지는 원래 값을 유지한다. (제자리 수정하면 d1·d3 까지 조용히 바뀐다)
- **자가 치유** — 이미 표류해 있던 원소도 저장 한 번으로 수렴한다.
- **모호하면 손대지 않는다** — 매칭이 0건이거나 2건 이상이면 동기화만 건너뛰고 `assignmentSyncReason` 으로 사실을 알린다.
- **하위 트랜잭션 강등** — 동기화 실패가 편집 자체를 죽이지 않는다.

## 4. 새로 만들 것

### 4-1. 슬롯 키 축 — "전체"가 정확히 무엇인가

전체 축의 대상 집합은 **`_posting_slot_key` 로 정의한다.** 임의 조건이 아니다.

```
대상 = work_logs 중
  job_posting_id = :posting
  AND date       = :date
  AND _posting_role_key(role, custom_role) = :roleKey
  AND _posting_slot_key(time_slot)         = :fromSlotKey
  AND status NOT IN ('cancelled', 'no_show')     -- 🔴 필수 (supabase-patterns §11)
```

세 가지 이유로 이 축이어야 한다:

1. **정원 판정과 같은 축이다.** `confirm_application` 이 정원을 `_posting_slot_key` 로 센다. 다른 축으로 묶으면 "화면에 한 슬롯으로 보이는데 일괄 변경은 일부만 잡는" 어긋남이 생긴다.
2. **미정 센티널 4종이 이미 접혀 있다.** R0(#409)가 `NULL`·`''`·`'미정'`·`'NEGOTIABLE'` 을 전부 `'미정'` 으로 접었다. 원문 문자열로 묶으면 R0 이 없앤 키 분열이 되살아난다.
3. **범위 문자열이 시작시각으로 접힌다.** 레거시 `'18:00-22:00'` 도 `'18:00'` 슬롯으로 잡힌다.

🔴 **소프트 취소 필터를 빠뜨리면 취소된 인원의 시간까지 바꾸고 그들에게 알림이 나간다.** 에러는 나지 않는다.

> ⚠️ **§10-1 로 보완됨** — 이 축은 **후보 집합**을 정의하는 데 그대로 쓰지만, 실제 대상은
> 구인자가 그중에서 고른 부분집합이다(사용자 결정 ④). 서버는 넘어온 id 가 전부 이 축에
> 속하는지 **검증**하는 데 이 축을 쓴다 — 축 자체는 살아 있고, 역할이 "선택"에서 "검증"으로 바뀐다.

### 4-2. 신규 RPC `update_posting_slot_time`

> ⚠️ **시그니처는 §10-4 가 정본이다.** 아래는 S6 원안이고, 사용자 결정 ④⑤로 인자
> `p_work_log_ids uuid[]`(대상 선택)가 추가되고 공고 원문 정원 이동이 계약에 들어온다.

```
update_posting_slot_time(
  p_job_posting_id uuid,
  p_date           text,
  p_role_key       text,
  p_from_slot_key  text,
  p_patch          jsonb    -- { startTime } | { timeUndecided: true }
) RETURNS jsonb
```

**계약은 `update_work_log_slot` 을 그대로 상속한다** — 시간 축만 받는다(역할·색상·메모는 전체 축에 의미가 없다). 미지의 키는 거부. `timeUndecided` 가 `startTime` 보다 우선.

**권한은 RLS `wl_update` 정확 재현 · 확대 0.** 단건 RPC 가 세운 선례를 그대로 따른다. 전체 축이라고 `is_admin()` 을 더하지 않는다 — 그럴 근거가 없다.

**잠금 순서는 `applications` → `work_logs`.** 기존 RPC 관례와 동일. 🔴 **N건을 돌 때는 `work_logs.id` 오름차순으로 정렬해 잠근다** — 순서가 없으면 두 구인자가 겹치는 슬롯을 동시에 편집할 때 데드락이 난다. 단건 RPC 에는 없던 위험이다.

**반환값은 건별 집계다:**
```json
{ "success": true, "total": 7, "updated": 7,
  "assignmentSynced": 6, "skipped": [{"workLogId":"…","reason":"ambiguous_match"}] }
```
단건 RPC 의 `assignmentSyncReason` 을 배열로 승격한 형태다. 🔑 **부분 성공을 숨기지 않는다** — 7명 중 1명의 지원서 동기화가 모호해 건너뛰었다면 구인자가 그 사실을 알아야 한다.

### 4-3. ~~공고 원문 슬롯 정의는 건드리지 않는다~~ 🔴 **폐기 — §10-2/§10-3 이 대체한다**

> 🔴 **이 절의 결론은 S7 실측으로 뒤집혔다.** 원문을 그대로 두면 **출발지 슬롯의 정원이
> 통째로 재개방**되어 같은 자리에 인원을 두 배로 확정할 수 있게 된다(§10-2 증거).
> 확정된 결정은 **"정원도 이동 인원수만큼 함께 옮긴다"**(사용자 결정 ⑤, §10-3)이다.
> 아래 세 근거 중 살아남은 것은 없다 — 왜 틀렸는지는 §10-2 에 항목별로 적었다.
> 다만 마지막 ⚠️ 문단의 **"근무표 헤더 원천을 실측하라"** 지시는 이행됐고 결과는 §10-5 에 있다.

~~`job_postings` 의 슬롯 정의(모집 요건)는 **바꾸지 않는다.**~~ 원안의 이유:

- 모집 요건은 **"무엇을 뽑았는가"** 의 기록이고, `work_logs.time_slot` 은 **"실제로 언제 나오는가"** 다. 둘은 다른 사실이다.
- 공고 원문을 함께 옮기면 **아직 확정되지 않은 지원자**의 정원 판정 축이 발밑에서 바뀐다. 지원 시점과 확정 시점의 슬롯이 달라져 `confirm_application` 이 엉뚱한 슬롯에 정원을 센다.
- 공고 자체를 바꾸는 것은 **공고 수정** 기능이지 3-C 가 아니다.

⚠️ **결과적으로 공고 원문과 실제 근무 시각이 갈라진다. 이것은 의도된 것이다.** 다만 근무표 UI 가 원문 슬롯을 헤더로 쓰고 있다면 "18:00 슬롯 아래에 19:00 카드"가 보일 수 있다 — S7 착수 시 **근무표 헤더가 무엇을 원천으로 삼는지 먼저 실측할 것.**

## 5. 사용자 결정 3(덮어쓰기)의 유일한 위험

전체 변경은 개별 조정을 무조건 덮어쓴다. 구현은 단순하지만 **사람 사이의 문제**가 남는다: 어제 개별 합의로 20:00 로 옮긴 스태프가, 오늘 일괄 변경으로 아무 설명 없이 19:00 으로 되돌아간다.

**설계상 대응은 알림 하나뿐이고, 그 알림은 이미 정확하다.** Case 2-B 본문이 `20:00 → 19:00` 과 취소 힌트를 함께 싣는다. 스태프는 무엇이 바뀌었는지 보고 못 맞추면 취소를 요청한다 — 결정 2 와 정확히 맞물린다.

🔑 **추가로 만들 것은 없다. 다만 S7 은 이 시나리오를 테스트로 고정해야 한다** — "개별 조정된 행이 일괄 변경에 포함되고, 알림에 이전값이 개별 조정값으로 찍힌다".

## 6. 함정 (착수 전 읽을 것)

1. 🔴 **소프트 취소 필터 누락** — `status NOT IN ('cancelled','no_show')` 없으면 취소자에게 알림이 간다. 무증상.
2. 🔴 **잠금 순서 미지정 데드락** — N건 반복은 단건에 없던 위험이다. `ORDER BY id` 필수.
3. 🔴 **목적지 슬롯 정원 충돌** — 18:00 슬롯 7명을 19:00 으로 옮겼는데 19:00 에 이미 3명이 있으면 그 슬롯 인원이 10명이 된다. **정원 초과를 막을 것인가 허용할 것인가는 미결이다**(§7).
4. 🔴 **`assignments.timeSlot` 에 JSON null 금지** — zod 가 `z.string()` 이라 null 이면 지원서가 통째로 증발한다(A2 사고). 미정은 `'미정'` 문자열.
5. ⚠️ **0패딩 정규화를 RPC 안에서 할 것** — `'9:00'` 과 `'09:00'` 이 다른 슬롯으로 쪼개진다. CHECK 제약에 맡기면 23514 원시 에러가 샌다.
6. ⚠️ **`application_id IS NULL` 행**(`add_direct_staff` 로 직접 배치한 스태프)은 동기화 대상이 아니지만 **알림 대상은 맞다.** 취소 힌트만 빠진다 — 트리거가 이미 처리한다.
7. ⚠️ **E2E 는 `npm run quality` 범위 밖이다.** 시간 관련 상수·문구를 건드리면 `e2e/` 를 별도 Grep 할 것.

## 7. ~~🔴 남은 미결~~ ✅ **해소됨 (2026-08-04, §10-3)**

> ✅ **결론: 정원 초과 상황 자체가 생기지 않는다.** 사용자 결정 ⑤로 공고 원문 정원이 실제 배치를
> 따라 함께 이동하므로, 목적지 슬롯의 정원도 인원수만큼 늘어난다. 아래 세 선택지(①②③)는
> "정원이 고정돼 있다"는 전제 위에 서 있었고 그 전제가 §10-3 으로 사라졌다.

**목적지 슬롯에 이미 인원이 있으면 어떻게 하는가?**(함정 3) — 당시 논의:

이번 결정 3건은 "누가 이기는가"를 정했지만 이 경우는 다루지 않았다. 선택지는 셋이다: ① 정원 초과를 허용하고 경고만 · ② 초과가 되면 통째로 거부 · ③ 초과분만 건너뛰고 보고. 사용자 결정 1·2·3 의 방향(단순·즉시·기존 경로)을 따르면 ①이 일관되지만, 정원은 R0 이 우회를 막으려고 세운 불변식이라 가볍게 열 수 없다.

## 8. S7 테스트 계획 (RED 먼저)

- 슬롯 7명 일괄 변경 → 7행 갱신 · 알림 7건 · 각 수신자 1건
- 취소된 1명 포함 슬롯 → 취소자는 갱신·알림 **모두 제외**
- 개별 조정된 1명 포함 → **덮어써지고** 알림 이전값이 개별 조정값
- `application_id` NULL 행 → 갱신·알림 O, 취소 힌트 X, `assignmentSynced` 집계에서 제외
- assignment 원소가 `dates:[d1,d2,d3]` 를 덮을 때 d2 슬롯 변경 → d1·d3 값 불변 (#407 회귀 가드 재사용)
- 미정 센티널 4종이 한 슬롯으로 묶이는지 (`NULL`/`''`/`'미정'`/`'NEGOTIABLE'`)
- `'9:00'` 입력 → `'09:00'` 저장
- 권한 없는 사용자 → `PERMISSION_DENIED`, 0행 갱신
- 동시 편집 2건 → 데드락 없음

🔴 **Red-Green 을 실제로 돌릴 것** — 통과만 확인하면 그 테스트가 무엇을 잡는지 모른다.

# 10. S7 개정 (2026-08-04) — 실측 결과와 추가 결정 3건

> 이 장이 §1~§9 보다 **우선한다.** S6 은 코드를 읽고 설계했고, S7 은 착수 전 실측에서
> 설계의 전제 하나가 사실과 다름을 발견했다. 아래는 그 실측과, 그로 인해 사용자가 내린 결정이다.

## 10-1. 사용자 결정 ④ — 대상은 슬롯 전원이 아니라 **구인자가 매번 고른다**

시간 변경을 누르면 그 슬롯의 스태프 목록이 뜬다. **기본은 전원 체크**이고 구인자가 일부를 해제할 수 있다.
개별 조정된 사람은 목록에 그 사실이 라벨로 보인다(예: `강··(개별 20:00)`).

```
[19:00 으로 변경]  ▸  대상 선택

 18:00 딜러 7명
  ☑ 김··  ☑ 이··  ☑ 박··  ☑ 최··
  ☑ 정··  ☐ 강··(개별 20:00)  ☑ 조··

 ⚠ 19:00 슬롯은 현재 3명 / 정원 5명
    6명 옮기면 9명이 됩니다

              [취소]   [6명 변경]
```

**설계상 귀결:**

- §4-1 의 슬롯 키 축은 **버리지 않는다.** 역할이 바뀔 뿐이다 — 후보 집합을 만드는 데 쓰고,
  서버는 넘어온 `work_log_id` 가 **전부 그 축에 속하는지 검증**하는 데 쓴다. 축 밖 id 는 **거부**(fail-closed).
  이렇게 해야 "화면에 한 슬롯으로 보이는 것과 서버가 묶는 것이 같다"는 §4-1 의 불변식이 산다.
- §5 의 위험(개별 조정이 조용히 덮어써진다)이 **실질적으로 완화된다.** 구인자가 그 사람을 보고
  체크를 해제할 수 있기 때문이다. 다만 **기본이 전원 체크**이므로 §5 의 시나리오는 여전히 성립하고,
  §8 의 해당 테스트는 그대로 유지한다.

## 10-2. 🔴 실측 — work_logs 만 옮기면 **출발지 슬롯 정원이 통째로 재개방된다**

§4-3 은 공고 원문을 안 건드리기로 했다. 그러면 이런 일이 벌어진다.

`confirm_application` 의 정원 판정은 **원천이 다른 두 값**을 비교한다
(`20260803120000_time_slot_sentinel_unification.sql:186-195`, 215):

| 값 | 원천 | 18:00 → 19:00 이동 후 |
|---|---|---|
| `v_existing` | `work_logs` 를 `_posting_slot_key(wl.time_slot)` 로 집계 | **7 → 0** |
| `v_capacity` | `job_postings.schedule->'requirements'` 원문 | **7 그대로** |

→ `v_existing(0) + requested ≤ v_capacity(7)` 이 통과한다. **18:00 슬롯에 신규 7명을 다시 확정할 수 있고,
그 날 그 역할 인원이 14명이 된다.** 에러는 나지 않는다. 이건 R0(#409)가 막으려던 정원 우회와 결과가 같다.

같은 원인으로 **화면에서 확정 인원이 사라진다**:

- 집계: `count_posting_confirmed_by_slot` 이 `work_logs` 를 `_posting_slot_key` 로 묶는다
  (`archive/20260525040100_posting_count_slot_role_key_normalization.sql:60-72`).
- 조회: `postingSurfaceModel.ts:468` 이 `${date}__${slotKey}__${roleKey}` 로 찾는데,
  `slotKey` 는 **공고 원문 슬롯**에서 파생된다(`slotHydrateKey` → `postingHydrateKeys.ts:93`).
- → 18:00 슬롯이 `0/7` 로 보이고, 19:00 은 원문에 없어 아예 렌더되지 않는다.

**§4-3 의 세 근거가 왜 틀렸는가:**

1. *"모집 요건은 무엇을 뽑았는가의 기록"* — 그렇다면 기록이 **거짓이 된다.** 원문은 18:00 에 7자리가
   비어 있다고 계속 말하는데 실제로는 그 시간에 아무도 없다. 게다가 공고는 이미 수정 가능한
   살아 있는 문서다(`notify_on_job_posting_update` 가 `schedule` 변경을 '근무일'로 알린다).
2. *"미확정 지원자의 정원 판정 축이 발밑에서 바뀐다"* — 사실이지만, 안 바꾸면 **더 나쁘다.**
   자리가 실제로 줄었는데 줄지 않은 척하면 그 자리에 사람을 또 받는다.
3. *"공고 자체를 바꾸는 건 공고 수정 기능"* — 공고 수정은 `work_logs` 를 건드리지 않으므로
   확정된 스태프에게 반영되지 않는다. 두 기능이 각자 반쪽만 움직여 **양방향 표류**를 만든다.

## 10-3. 사용자 결정 ⑤ — **정원도 이동 인원수만큼 함께 옮긴다**

```
6명을 18:00 → 19:00 으로 이동할 때

공고 원문 requirements
  전  18:00 딜러 count 7 · 19:00 딜러 count 3
  후  18:00 딜러 count 1 · 19:00 딜러 count 9

work_logs: 선택된 6행의 time_slot 18:00 → 19:00
```

의미론은 **"정원은 실제 배치를 따라간다"** 이다. 결과:

- 출발지 `v_existing 1 / capacity 1` — 재개방 없음 ✅
- 목적지 `v_existing 9 / capacity 9` — 초과 없음 ✅ (§7 미결이 이래서 소멸한다)
- 공고 표면 표시 정합 ✅
- 목적지 슬롯이 원문에 없으면 **신설**한다(count = 이동 수).
- 출발지 count 가 0 이 되면 그 역할 항목을 남길지 지울지는 §10-7 참조.

🔑 **총합 보존이라는 좋은 성질이 따라온다.** `_total_positions_from_schedule` 은 모든
날짜×슬롯×역할 `count` 의 **총합**이다(`20260718000000_seat_basis_filled_total_positions.sql:22-29`).
정원을 옮기기만 하면 총합이 불변이므로:

- `total_positions` 불변 → `capacity_full ↔ active` 자동 전이가 **일어나지 않는다**(`:46-58`)
- → 그에 딸린 마감 알림 연쇄도 없다

⚠️ **미확정 지원자는 자리가 줄어든 것을 화면에서 알 수 있어야 한다.** 18:00 에 지원해 둔 사람의
자리가 6개 사라지는 것은 사실 반영이지만, 조용히 일어나면 안 된다(§10-6 이 이걸 알림으로 덮는다).

## 10-4. 사용자 결정 ⑥ — 알림은 **기존 배선 그대로**, 중복을 허용한다

`job_postings.schedule` 을 건드리면 `notify_on_job_posting_update` 가 깨어나
**그 공고의 활성 지원자 전원**(`confirmed`/`applied`/`cancellation_pending`)에게
'📝 공고 수정 안내 — 근무일이 변경되었습니다'를 보낸다
(`20260802170100_job_posting_update_changed_labels.sql:100-101`, 124-126, 180-193).

발송 결과:

| 대상 | 받는 알림 |
|---|---|
| 옮겨진 6명 | ② `schedule_change`(18:00 → 19:00 + 취소 힌트) + `job_updated`(근무일) |
| 안 옮긴 1명 | ① `job_updated`(근무일) |
| 미확정 지원자 | ① `job_updated`(근무일) — §10-3 의 ⚠️ 를 이게 덮는다 |

**억제하지 않는다.** 억제하려면 트리거 함수를 재정의해야 하는데(GUC 플래그 배선),
그건 이미 검증된 알림 경로에 회귀 위험을 새로 만드는 일이고, 미확정 지원자가 자리 축소를
모르게 만든다. 🔑 **결과적으로 §3-1 의 "3-C 는 알림 코드를 한 줄도 쓰지 않는다"가 그대로 지켜진다.**

## 10-5. 실측 — 근무표 헤더는 무해하다 (§4-3 의 착수 전 지시 이행)

**근무표(운영처 일자 상세)는 100% `work_logs` 원천이라 이 변경을 그대로 따라온다.**

- `get_venue_day_slots` 는 `job_postings` 의 슬롯 정의를 **전혀 조회하지 않는다.**
  `wl.time_slot` 을 그대로 반환하고 `ORDER BY wl.time_slot NULLS LAST, wl.staff_name` 로 정렬한다
  (최신 정의 = `20260710000002_baseline_schema_from_prod.sql:3125-3145`;
  같은 본문이 `archive/20260703000000_weekly_grid_read_rpc_workspace_guard.sql:98-123` 에도 있다).
- 화면은 **시각 헤더 자체가 없다.** 하루치를 **날짜 단일 그룹**으로 묶어 카드마다 시각을 보여준다
  (`venueDayDetailMapping.ts:54-77` `buildVenueDayGroup`).

→ §4-3 이 걱정한 "18:00 헤더 아래 19:00 카드"는 **근무표에서는 발생하지 않는다.**
실제 문제는 근무표가 아니라 **공고 표면과 정원 판정**이었다(§10-2).

🔑 교훈: 설계가 지목한 위험 지점과 실제 위험 지점이 달랐다. **착수 전 실측 지시가 값을 했다.**

## 10-6. 확정된 RPC 계약

```
update_posting_slot_time(
  p_job_posting_id uuid,
  p_date           text,
  p_role_key       text,
  p_from_slot_key  text,
  p_work_log_ids   uuid[],   -- 🔑 결정 ④ — 구인자가 고른 대상
  p_patch          jsonb     -- { startTime } | { timeUndecided: true }
) RETURNS jsonb
```

`update_work_log_slot`(#407)에서 **그대로 상속**하는 것:

- 시간 축만 받는다(역할·색상·메모는 전체 축에 의미가 없다)
- **미지의 키는 거부** · 각 키의 jsonb 타입도 검사(JSON null ≠ SQL NULL)
- `timeUndecided` 가 `startTime` 보다 **우선**
- **0패딩 정규화를 RPC 안에서** 한다(`'9:00'` → `'09:00'`)
- 권한은 **RLS `wl_update` 정확 재현 · 확대 0** — 전체 축이라고 `is_admin()` 을 더하지 않는다
- assignments 동기화의 **셀 단위 분해 · 자가 치유 · 모호하면 손대지 않기**
- 동기화 실패는 **하위 트랜잭션으로 강등**(편집은 살리고 동기화만 포기)

3-C 에서 **새로 더하는** 것:

- `p_work_log_ids` 가 (posting, date, roleKey, fromSlotKey) 축 + 소프트 취소 필터에 **전부 속하는지 검증**.
  하나라도 벗어나면 **전체 거부**(부분 적용은 슬롯을 갈라놓는다)
- 🔴 **`ORDER BY id` 로 잠근다** — N건 반복은 단건에 없던 데드락 위험이다
- `job_postings.schedule->'requirements'` 의 출발지 count `-= N` / 목적지 count `+= N`(없으면 신설)
- 반환값은 **건별 집계**, 부분 성공을 숨기지 않는다:

```json
{ "success": true, "total": 6, "updated": 6,
  "assignmentSynced": 5,
  "skipped": [{"workLogId":"…","reason":"ambiguous_match"}],
  "capacityMoved": { "from": {"slot":"18:00","count":1}, "to": {"slot":"19:00","count":9} } }
```

## 10-7. ✅ 구현 중 확정된 사항 (2026-08-04 S7 · 전부 실측으로 닫힘)

착수 시점의 미확정 5건은 전부 실측으로 닫혔고, 그 과정에서 **설계가 예상하지 못한 결함 3건**이 나왔다.

| # | 착수 시 질문 | 결론 |
|---|---|---|
| 1 | 출발지 정원 0 시 항목을 지울지 남길지 | **지운다.** 남겨도 `v_capacity > 0` 가드는 똑같이 스킵되므로(`20260803120000:215`) 보안 차이가 없고, 유령 슬롯을 남기지 않는 쪽이 데이터가 깨끗하다 |
| 2 | `job_postings` RLS UPDATE 술어 | `is_workspace_member OR is_posting_collaborator OR is_admin()`(baseline:13643) + RESTRICTIVE `status <> 'container'`(:13606). `work_logs.wl_update` 와의 **교집합 = 멤버 ∪ 협업자** — RPC 가 이것만 통과시킨다(리뷰 2인 실측 확증) |
| 3 | `enforce_jp_status_transition` 이 막는가 | **막지 않는다.** `UPDATE OF status` 컬럼 트리거라 SET 절에 status 가 없으면 발화조차 안 한다 |
| 4 | 고정공고 지원 여부 | **제외.** zod superRefine 이 요건 1개·슬롯 1개만 허용해(`jobPosting.schema.ts:219-233`) 슬롯을 더하면 공고가 검증 실패로 사라진다. 컨테이너도 제외(모집 요건 없음) |
| 5 | `check_xss_fields` 영향 | 무해. `title`·`description`·`contact_phone` 만 검사한다(`20260717093000:440`) |

### 구현 중 발견한 결함 3건 (전부 수정 + 회귀 테스트)

1. 🔴 **레거시 `headcount` 정원 키에서 총합 파손** — 총합 함수는 `COALESCE(count, headcount, 0)` 인데
   수술은 `count` 만 읽었다. 실측 `5 → 3`. 읽기·쓰기가 같은 키를 따르게 고쳤다.
2. 🔴 **초과 배정 슬롯에서 총합 팽창** — `GREATEST(count-n, 0)` 로 깎으면서 목적지엔 n 전액을 더했다.
   실측 `3 → 6`. **capacity_full 공고가 active 로 재개방**되는 경로였다. 실제 이동 가능한 만큼으로 clamp.
3. 🔴 **시트에서 묶음을 바꿔도 앞 시각이 남음** — 의도하지 않은 시각으로 실행될 수 있었다(클라).

### 코드로 닫지 않고 **기록만** 한 한계 2종

- **TOCTOU** — 축 검증과 잠금 사이 ms 급 창. 권한은 닫혀 있고(행별 재검증 + 신원 고정 트리거),
  닫으려면 잠금 순서를 뒤집어야 하는데 `cancel_application_atomically` 와 엇갈려 **더 나쁜 데드락**이 된다.
- ✅ **모순 알림 쌍 — 해소됨(사용자 결정 ⑦, 2026-08-04)**. 아래 §10-9 참조.

### 잔여 과제(별건으로 이관)

`v_capacity = 0` 을 "정원 미상=통과"가 아니라 "자리 없음=거부"로 바꾸는 것.
R0 이 심어 둔 관측 로그(`capacity=0 match`, `20260803120000:210-213`)로 데이터를 모은 뒤 판단한다.
레거시 공고 전체에 영향이 가므로 3-C 범위 밖이다.

1. **출발지 count 가 0 이 될 때** 역할 항목을 배열에서 지울지, `count: 0` 으로 남길지.
   지우면 그 슬롯에 지원해 둔 미확정 지원자의 `v_capacity` 가 0이 되어 **정원 가드가 통째로 스킵**된다
   (`20260803120000:215` 의 `v_capacity > 0` 조건). → **`count: 0` 유지가 안전해 보이나 실측 필요.**
2. `job_postings` 의 **RLS UPDATE 정책 정확한 술어** — 신규 SECDEF RPC 가 재현해야 한다(확대 0).

## 10-8. §8 테스트 계획에 추가할 항목

§8 의 9항목은 **전부 유효하다.** 아래를 더한다:

- 선택 부분집합만 이동 → 나머지 인원의 `time_slot` **불변**, 그들에게 알림 **없음**
- `p_work_log_ids` 에 **축 밖 id**(다른 슬롯·다른 역할·다른 날짜·취소된 행) 혼입 → **전체 거부**, 0행 갱신
- 공고 원문 count 이동 → 출발지 `-N` · 목적지 `+N` · **`total_positions` 불변** · **status 전이 없음**
- 목적지 슬롯이 원문에 **없을 때** → 슬롯 신설 후 count = N
- 이동 후 `confirm_application` 으로 출발지 슬롯 재확정 시도 → **정원 초과로 거부**(§10-2 회귀 가드)
- 이동 후 공고 표면 hydrate 키 조회 → 출발지·목적지 **둘 다 정확한 확정 수**

## 10-9. 사용자 결정 ⑦ — 모순 알림 쌍은 **문구 중립화**로 닫는다 (2026-08-04)

§10-4 의 결정 ⑥("알림은 기존 배선 그대로")은 **②의 실제 문구를 모르는 상태**에서 내려졌다.
S7 착지 세션에서 문구를 실측하고 사용자에게 다시 물어 닫았다.

**실측 1 — 모순은 조건부가 아니라 무조건이다.**
`v_date_changed` 는 `work_date`·`work_dates`·`schedule` 중 **하나라도 달라지면** 참이다
(`20260803120000:520-523`). 3-C 는 정원 count 만 옮겨도 `schedule` 을 쓰므로 라벨 '근무일'이 붙고
계약 보유자 분기가 **항상** 발화한다.

옮겨진 스태프가 실제로 받던 두 통:

| | 문구 | 링크 |
|---|---|---|
| ① `schedule_change` (Case 2-B) | 출근 예정 시간이 변경되었습니다: 18:00 → 09:00 | 근무표 |
| ② `job_updated` (계약 보유자 분기) | 근무일이 변경되었습니다. '…' 공고를 확인해 주세요. **이미 확정된 내 근무 시간은 바뀌지 않습니다** — 근무표에서 확인해 주세요. | `/schedule` |

②의 단언은 3-C 이전엔 참이었다("공고=광고, work_logs=계약"). 3-C 가 그 전제를 깼다.

**실측 2 — 회귀 표면이 좁다.** 이 문구를 단언하는 테스트·클라이언트 참조는 **0건**이었다
(전수 grep — 참조처는 함수 정의부 1곳과 3-C 마이그 주석 1곳뿐).

**결정: 문구만 중립화한다.**

```
변경 전: ' 이미 확정된 내 근무 시간은 바뀌지 않습니다 — 근무표에서 확인해 주세요.'
변경 후: ' 확정된 내 근무 시간은 근무표에서 확인해 주세요.'
```

분기 조건·수신자·링크·우선순위·`data` 는 **전부 불변**이다. 마이그
`20260804130000_job_posting_update_contract_body_neutral.sql` 이
`20260803120000:430-644` 를 그대로 옮기고 이 한 문장만 교체한다 — 시그니처가 같으므로
**파리티 함수 수도 불변**이다.

**기각한 대안 2종**

- **ⓐ 그대로 두기** — 옮겨진 당사자에게 거짓 문장이 계속 나간다. 시간·출근에 닿는 오정보라 기각.
- **ⓒ 3-C 실행 중 ② 억제(GUC 플래그)** — 검증된 알림 경로에 새 분기를 넣는 일이고,
  같은 공고의 **미확정 지원자**가 자리 축소를 모르게 된다. §10-4 가 억제를 기각한 이유가 그대로 유효하다.
