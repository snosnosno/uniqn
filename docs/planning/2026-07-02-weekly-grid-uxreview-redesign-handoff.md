# 핸드오프 — 주간 배치 "공고 그리드" 전면 UX/설계 리뷰 & 개선 (다음 세션 메인 프롬프트)

> 작성 2026-07-02. 이 문서를 **메인 프롬프트**로 시작하라. 목표는 기능 완성이 아니라 **더 좋은 UI/UX**다.

## 0. 미션 (권한 넓게)

주간 배치 그리드(사장이 부르는 "공고 그리드") 기능을 **UI/UX·설계 관점에서 전면 재검토하고 더 좋게 만든다.** 다음이 명시적으로 허용된다:

- 기존 워크플로우·유저플로우와의 **마찰 / 중복 / 개념 과잉**을 적극적으로 찾아 제거.
- 필요하면 **현재 설계(venue = 숨김 컨테이너 공고)를 뒤엎어도 된다.** 점진 개선이든 부분 재설계든 전면 재설계든, 기준은 오직 "운영자에게 더 나은 경험".
- 단, **실제 스키마 제약과 이미 출하된 것**을 이해한 위에서. 재설계 제안은 마이그레이션·백compat·롤아웃 계획을 포함해야 한다.

이번 세션은 **문제 재정의부터** 시작한다("이걸 왜, 이렇게 만들었나?"). 코드부터 만지지 말 것.

## 2. 현재 핵심 설계 & 그 대가 (재검토 1순위)

1. **venue = 숨김 공고 `status='container'`**. 이유: `work_logs.job_posting_id`가 **NOT NULL**(6테이블 + 5트리거가 이 FK 참조)이라 근무기록은 공고에 매달려야 함 → 운영처를 "보이지 않는 공고"로 만들어 RLS·QR·정산·게시판을 **공짜 상속**. **대가**: "공고"라는 한 단어가 두 뜻(진짜 공고 vs 데이터 그릇)을 가짐 → 모든 목록/집계/파싱 경로가 **'container'를 빼는 걸 잊지 말아야** 하는 영구 세금(R5 읽기 Zod, `.neq('status','container')` 방어, enum 발산 위험). **생성 UI 누락(방금 고침)도 이 오버로딩의 증상**이었다 — 운영처가 일급 객체가 아니라 공고에 모자 씌운 것이라 생성 화면이 조용히 빠졌다.
2. **3계층 개념**: 워크스페이스 → 운영처(venue) → 공고. 운영자가 이 셋을 구분해야 한다. **대부분 홀덤펍 사장은 가게 1개 = 워크스페이스 1개 = 운영처 1개**일 텐데 3층이 정당한가? (가장 날카로운 재검토 지점.)
3. **E1 venue 스팬 집계**: 운영처 인원 = 컨테이너 직접배치 + 그 venue의 open 공고 인원 합산(`venue_span_posting_ids` SSOT).
4. **스태프 추가 경로가 둘**: 그리드 `AddSlotSheet`(풀/전화/공고열기) vs 일반 스태프관리 `AddStaffModal`. 중복/혼선?
5. **진입점**: "내 공고" 탭 안 버튼 → 별도 그리드 화면. 기존 공고 관리와 **분리된 멘탈모델**.

## 3. 반드시 던질 질문 (유저·워크플로우 마찰)

- 홀덤펍 사장의 **실제 주간 루틴**은? 이 그리드가 그 루틴에 자연스러운가, 아니면 새 개념(운영처·컨테이너)을 강요하나?
- **"운영처"가 사장에게 직관적인가?** 워크스페이스와 뭐가 다른가? 사장 눈엔 그냥 "우리 가게"인데 왜 워크스페이스 + 운영처로 쪼개나? → **운영처를 워크스페이스에 흡수/자동화**하면 3계층이 2계층이 되고 생성 UI 자체가 사라질 수도.
- 그리드 ↔ 기존 **"내 공고" / "내 스케줄" / 공고작성** 흐름의 중복·충돌 지도.
- **대회사(대회 D-7 집중)** 에게 "주간 상시 배치" 그리드가 맞나? 대회는 다른 모델(이벤트 단위)이 필요할 수도.
- 앱 정체성 **"단발 알바 매칭"** 과 "상시 단골 배치" 사이의 긴장. 둘을 한 화면에 어떻게 화해시키나?
- 캘린더 그리드가 최선의 표현인가? 리스트/보드/주간 시프트표 등 대안은?

## 4. 접근 (권장 스킬 체인)

1. `/office-hours` 또는 `superpowers:brainstorming` — 설계 뒤엎기 허용이므로 **문제·수요 재정의부터**.
2. 코드·플로우 실측: 그리드 화면 / `AddSlotSheet` / `AddStaffModal` / `VenueSelector` / 정산 / QR 경로를 기존 공고·스케줄 플로우와 **나란히 비교해 중복 지도** 작성.
3. Playwright 웹구동(로컬 플래그 ON, 시드 운영처)으로 **실제 운영자 플로우를 직접 밟으며** 마찰 지점을 스크린샷으로 채증.
4. `/plan-design-review` — UI/UX 차원별 0–10 점수 + "10점이 되려면".
5. **대안 설계 2–3개** 제시(현행 유지+개선 / 개념 단순화[운영처↔워크스페이스 통합·자동화] / 표현 전환[그리드→다른 UI] / 전면 재설계) → 트레이드오프 → 추천. 재설계안은 스키마/마이그/백compat 명시.
6. 사용자 합의 후 스펙 → 계획 → 구현. **구현은 맨 마지막.**

- `work_logs.job_posting_id` **NOT NULL**(6테이블 + 5트리거 참조) — 이 FK를 nullable로 바꾸는 스키마 뒤엎기는 금지 스코프. 재설계는 이 위에서.
