# 근무 시간 편집 통일 설계 — 예정·실적 분리와 한 시트 수렴 (2026-08-06)

> 목적: 같은 사람의 같은 하루를 **어느 화면에서 열든 같은 창에서 같은 규칙으로** 수정하게 한다.
> 근거: 코드 실측(편집 표면 4곳·RPC 전문·리포지토리 2종) + 사용자 도메인 결정 3건(2026-08-06).
> 상태: **설계 문서** — 구현 전 승인 대상. 구현 세션은 전용 워크트리에서(메모리 규칙).
> 선행 정본: `docs/analysis/2026-08-03-time-model-redesign.md`(시간 모델 3원칙). 본 문서는 그 §원칙3(쓰기는 RPC만)의 실적축 이행분이다.

## 0. 확정된 도메인 결정 (사용자, 2026-08-06)

- **D1. 예정과 실적의 역할 분리.** 출근 **예정** 시각은 스태프가 보고 출근하기 위한 **안내값**이며 근태 상태를 절대 바꾸지 않는다. **실제** 출근은 QR 또는 사람의 직접 수정으로만 기록되고, 그때만 상태가 `checked_in`으로 전환된다.
- **D2. 통합 범위 = 3곳 전부 동일.** 근무표 · 공고 스태프관리 · 정산 탭이 같은 편집 창을 쓴다.
- **D3. 통합 대상 = 편집기 전체.** 시간 3축뿐 아니라 역할·구분 색·배치 메모까지 한 창에 모은다.
- **D4. 정산 완료 건은 전체 읽기 전용.** 부분 잠금(실적만 잠금)은 "왜 이건 되고 저건 안 되지"를 만든다.
- **D5. 일괄 변경은 이번 범위 제외.** ⚠️ 시간모델 D2("일괄 편집 RPC 만들지 않는다")는 **3-C 작업에서 이미 뒤집혔다** — `update_posting_slot_time` RPC(`20260804120000`)와 UI(`SlotTimeChangeSheet.tsx`)가 이미 존재하고 `VenueDayPanel`에 배선돼 있다. 제외하는 이유는 "만들지 않기로 했으니까"가 아니라 **축이 다르기 때문**이다(3-C = 공고+역할키+출발시각 묶음 / 본 설계 = 개인 1행). 관계 정의는 §4-3.

## 1. 문제 — 필드가 나뉜 게 아니라 화면별로 예측이 안 된다

같은 사람의 같은 하루인데 고칠 수 있는 항목이 화면마다 다르다.

| 진입점 | 출근 예정 | 실제 출퇴근 | 역할 | 색 | 메모 | 빼기 |
|---|---|---|---|---|---|---|
| 근무표 `EditSlotSheet` | ✅ | △ 입구만 (조건부) | ✅ 칩 | ✅ | ✅ | ✅ |
| 공고 스태프관리 | ❌ | ✅ | ✅ 별도 모달 | 👁 표시만 | 👁 표시만 | ✅ |
| 정산 탭 | ❌ | ✅ | ✅ 별도 모달 | ❌ | ❌ | ❌ |

👁 = 값이 화면에 보이는데 그 화면에서는 고칠 수 없음.

### 1-1. 확인된 결함 5건

**① 예정 시각이 몰래 실제 출근으로 저장된다 (사용자 신고의 원인)**

`src/components/employer/settlement/WorkTimeEditor.tsx:114-121` — 실제 출근 기록이 없으면 예정 시각(`timeSlot`)을 출근 칸에 프리필하고 `isStartTimeUndefined=false`로 둔다. 주석에도 "저장 시 실제 출근으로 기록됨"이라 적혀 있다.

퇴근만 고쳐도 저장 시 그 프리필 값이 `check_in_ts`로 기록되고, `src/repositories/supabase/workLogTimeStatus.ts:83`이 `checked_in`을 파생해 **손대지 않은 근태 상태가 뒤집힌다.** D1 위반.

같은 함정을 근무표 `EditSlotSheet`는 이미 "기본값 주입 금지"로 막아뒀다(`resolveSlotTimePayload` + 저장 게이트). 한쪽만 반대로 가 있다.

**② 근무표에서 실적 편집 입구가 조건부로 사라진다**

`src/components/workSchedule/VenueDayPanel.tsx:177` — `editingSlot.isContainer`인 슬롯에만 `attendance`를 주입한다. 공고 스팬 슬롯에서는 "출퇴근 시간 수정" 버튼 자체가 렌더되지 않아, 사용자 체감이 "근무표는 예정만 고칠 수 있다"가 된다.

**③ 근무표 역할 변경이 이력을 남기지 않는다**

`supabase/migrations/20260802180000_update_work_log_slot_rpc.sql` — `role`만 UPDATE하고 `role_change_history`를 건드리지 않는다. 반면 `ConfirmedStaffRepository.ts:340-360`(`changeRoleWithTransaction`)은 append한다. **같은 행위가 경로에 따라 이력이 남거나 사라진다.**

**④ 역할 정원 마감 검사가 서버에 없다**

`RoleChangeModal`은 `filledByRole`로 마감 역할 칩을 클라에서 비활성화한다. 그러나 `update_work_log_slot` RPC 전문에 capacity 검사가 없고, 근무표 역할 칩에도 마감 판정이 없다. **근무표 경로로는 마감된 역할에 인원을 밀어 넣을 수 있다.**

**⑤ `custom_role` 유령**

RPC는 `custom_role`을 의도적으로 건드리지 않는다(파일 내 주석 271-274에 명시). `other`(+`customRole`)였던 사람을 근무표에서 `dealer`로 바꾸면 `custom_role`이 남은 채 표시 경로에 따라 옛 커스텀 역할명이 되살아날 수 있다. `changeRoleWithTransaction`은 `isStandardRole` 분기로 `custom_role: null`을 함께 쓴다.

### 1-2. 명명 혼동 주의

`work_logs.notes`(배치 메모, RPC의 `memo` 키가 쓰는 컬럼 — 마이그레이션 259행)와 `applications.notes`(확정 시 메모, `ConfirmModal.tsx:72`)는 **다른 컬럼인데 이름이 같다.** 통합 편집기 라벨은 **"배치 메모"** 로 고정한다.

### 원칙 2가 만드는 UX — 프리필 대신 원탭 복사

실적 칸은 비어 있으면 **비운 채로** 둔다. 대신 옆에 회색 힌트로 `예정 18:00`을 보여주고 **[예정대로 기록]** 버튼을 단다.

> 비유: 예약 장부에 "7시 예약"이라 적혀 있다고 해서 손님이 온 걸로 처리하지 않는다. 손님이 오면 그때 도착 시각을 적는다. 버튼은 "예약 시간 그대로 도착했다"를 한 번에 적어주는 도장이다.

결함 ①의 정답은 "채워두기"가 아니라 "사장이 의도한 순간에만 복사되기"다.

## 3. 화면 설계

```
┌ 근무 수정 ──────────────────────────────────
│ 홍길동 · 8월 6일                   [출근 예정]   ← 상태 배지(읽기 전용)
├────────────────────────────────────────────
│ 근무 약속                                        ← 사전에 정하는 것
│   출근 예정   [18:00]   □ 미정
│   역할        (딜러) 플로어 서빙 …               ← 마감 역할 비활성 + "(마감)"
│   구분 색     ● ● ● ●
├────────────────────────────────────────────
│ 실제 출퇴근                                      ← 당일·사후 기록
│   출근        [  —  ]   예정 18:00  [예정대로 기록]
│   퇴근        [  —  ]
│   수정 사유   (선택)
├────────────────────────────────────────────
│ 배치 메모     [                              ]
├────────────────────────────────────────────
│  [빼기]                        [취소]  [저장]
└────────────────────────────────────────────
```

### 3-1. 섹션 라벨이 시간축을 설명한다

"근무 약속" / "실제 출퇴근" 두 라벨만으로 **왜 예정에는 종료가 없고 퇴근은 실적에만 있는지**가 드러난다(시간모델 D0 — 예정 퇴근 시각은 만들지 않는다).

### 3-2. 상태 배지 — 저장 전에 결과를 보여준다

실적 출근을 입력하면 배지가 `출근 예정 → 출근`으로 즉시 바뀐다. 저장 후에 상태가 변한 걸 발견하는 게 아니라, 저장 전에 알 수 있다. D1이 화면에 그대로 드러난다.

파생 규칙은 현행 `resolveWorkTimeStatus`와 동일하다(출근+퇴근 → `checked_out` / 출근만 → `checked_in` / 없음 → `scheduled`, `no_show`·`cancelled`는 제외).

### 3-3. 정산 완료 건 (D4) — ⚠️ 현행 대비 축소임을 명시

전체 읽기 전용 + 상단 한 줄: `정산이 완료돼 수정할 수 없어요.` 진입 자체는 허용해 값 확인은 가능하게 한다.

**이것은 현행 동작을 좁히는 결정이다.** 지금 `EditSlotSheet`는 정산 완료건이어도 `attendance.settled`로 **실적 입구만** 막고 예정·역할·색·메모 저장은 통과시킨다. D4 이후로는 "정산 끝난 뒤 배치 메모 정정"이 불가능해진다.

예측 가능성(어디를 눌러도 같은 답)과 맞바꾼 것이며, 실사용에서 "정산 후 메모 수정" 요구가 나오면 **메모만 예외로 여는 것**이 다음 후보다(색·역할·시간은 정산 근거라 잠금 유지).

### 3-4. 진입점별 차이 — 시간·역할·색·메모는 없음, "빼기"만 맥락 의존

근무표 카드 · 스태프관리 카드 · 정산 상세 → 전부 같은 시트. 슬롯 종류(`isContainer`)에 따른 항목 증발(결함 ②)을 없앤다.

**"빼기"만 예외다.** 세 곳의 의미가 실제로 다르기 때문이다(근무표=소프트 취소 `status='cancelled'`, 스태프관리=`removeStaff`, 정산=해당 없음). 시트 prop으로 제어하되, **이건 D2가 없애려던 "화면마다 다름"의 재발이므로 다음 규칙으로 고정한다**:

> 시트는 **시간·역할·색·메모 4축에 대해서만** 진입점 무관 동일을 보장한다. 파괴적 액션(빼기)은 진입 맥락의 것이며 시트의 것이 아니다. 따라서 **빼기는 시트 푸터가 아니라 각 화면의 카드 액션에 남긴다.**

이러면 시트는 순수 편집기가 되고, "저장" 하나만 갖는다. 근무표 `EditSlotSheet`의 현행 빼기 버튼은 슬롯 카드 액션으로 이동한다.

## 4. 서버 설계 — RPC 하나로 수렴

`update_work_log_slot`을 확장해 **예정·실적·역할·색·메모를 한 트랜잭션**으로 처리한다. 기존 jsonb 패치 계약(`p_patch ? 'key'`로 미제공/비움 3상 구분)을 그대로 이어받아 키를 추가한다.

| 패치 키 | 대상 컬럼 | 현행 위치 |
|---|---|---|
| `startTime` / `timeUndecided` | `time_slot` | ✅ 기존 RPC |
| `staffRole` | `role` (+ `custom_role` 정리 신설) | ⚠️ 기존 RPC (custom_role 누락) |
| `color` / `memo` | `color` / `notes` | ✅ 기존 RPC |
| `checkIn` / `checkOut` | `check_in_ts` / `check_out_ts` | 🆕 이관 (현재 직접 UPDATE) |
| `reason` | `modification_history` append | 🆕 이관 (현재 클라 append) |

### RPC 안으로 흡수되는 것

- **상태 파생** — `resolveWorkTimeStatus` 규칙을 서버로. 지금은 클라 헬퍼에만 있어 경로가 늘 때마다 어긋날 수 있다(주석에 SET-1 사고 기록됨).
- **역할 이력** — `role_change_history` append (결함 ③).
- **역할 정원 검사** — 마감 역할 거부 (결함 ④). 클라 비활성(UX) + 서버 거부(정합) 두 겹.
- **`custom_role` 정리** — 표준 역할 전환 시 `custom_role = NULL` (결함 ⑤).
- **실적 수정 이력·알림** — `modification_history` append → 기존 `notify_on_work_log_update` 트리거가 그대로 발화.

### 부산물 — R4(직접 UPDATE REVOKE)가 열린다

메모리에 R4 선행 조건이 "`SettlementRepository.ts:372`·`:648` RPC화"로 기록돼 있고, 이 때문에 R4가 막혀 있었다. 본 설계는 **실적 쓰기 2경로**(`ConfirmedStaffRepository.ts:444`, `SettlementRepository.ts:301`)를 RPC로 이관하므로 그 선행 조건이 해소된다.

⚠️ REVOKE 자체는 본 범위에 포함하지 않는다 — 구버전 앱 공존 기간이 끝나야 한다(시간모델 R4 조건). 본 설계는 **REVOKE를 가능하게 만드는 데까지**다.

### 4-3. 기존 3-C 일괄 변경(`update_posting_slot_time`)과의 관계

`time_slot` 쓰기 경로는 **셋**이다. 본 설계가 수렴시키는 것은 ①②뿐이다.

| # | 경로 | 축 | 본 설계에서 |
|---|---|---|---|
| ① | `update_work_log_slot` (개인) | work_log 1행 | ✅ 확장 대상 |
| ② | `updateWorkTimeWithTransaction` 2종 (실적 직접 UPDATE) | work_log 1행 | ✅ ①로 흡수 |
| ③ | `update_posting_slot_time` (3-C 일괄) | 공고 + 역할키 + 출발 시각 묶음 | ⛔ **그대로 둔다** |

③은 "이 공고, 이 역할, 18시 출발인 사람 전원을 19시로"라는 **묶음 축**이라 개인 편집으로 대체할 수 없다. 두 경로가 같은 컬럼을 쓰지만 축이 다르므로 공존이 맞다.

⚠️ **단, ①에 새로 넣는 규칙(역할 정원 검사·`custom_role` 정리·상태 파생)은 ③에도 같은 판정이 필요한지 P0-b 착수 시 대조할 것.** ③은 시각만 바꾸므로 역할 관련 규칙은 무관하나, 상태·알림 판정은 겹칠 수 있다.

### 4-4. QR 체크인 경로는 건드리지 않는다

QR 체크인 RPC도 `check_in_ts`를 쓴다(`20260727160000_qr_checkin_status_whitelist.sql` 등). SECDEF이므로 직접 UPDATE REVOKE(후속 R4)에도 살아남는다. D1의 "실제 출근 = QR 또는 직접 수정" 중 QR 축이 여기다 — **본 설계는 사람이 손으로 고치는 축만 다룬다.**

### 원자성이 필요한 이유

지금 구조로 통합하면 "예정=RPC + 실적=직접 UPDATE" **두 번 호출**이 되어, 사장이 3축을 함께 고쳤을 때 한쪽만 성공하는 상태가 생긴다. 그 결과가 "예정은 19시로 바뀌었는데 출근 기록은 옛날 값"처럼 **정산 금액에 직결되는 불일치**다. 한 트랜잭션이어야 한다.

### 5-1. P0-a가 필요한 이유 — 게이트가 아니라 데이터가 없다

`VenueDaySlot`(`src/repositories/interfaces/IWorkScheduleRepository.ts:11-27`)에는 `checkInTime`/`checkOutTime`/`payrollStatus`/`date`가 **없다.** 그래서 `VenueDayPanel`이 `useConfirmedStaff(venueId)`로 컨테이너 직속만 따로 해소하는 것이고, `isContainer` 게이트는 그 **결과**지 원인이 아니다.

공고 스팬 슬롯에서 실적을 편집하려면 읽기 RPC가 그 값을 실어 와야 한다. "게이트 한 줄 제거"가 아니라 **서버 선행 작업**이다.

### 5-2. 알림 판정은 착수 전 결정 (미결 아님)

`notify_on_work_log_update`는 **work_logs UPDATE 시 6가지를 통합 처리**한다(`20260802093000_notify_settlement_revert_and_cancel_hint_gate.sql:413` — 취소 / 이력 기반 근무시간 변경 / `time_slot` 변경 / 정산 완료 / 지급 완료 되돌리기 / 음수 정산 admin broadcast).

한 트랜잭션에서 예정과 실적을 함께 바꾸면 **이 트리거 하나가 2종을 동시에 판정해 스태프에게 알림 2발**이 간다. P0-b RPC를 쓰려면 트리거 전문을 읽고 정책을 먼저 정해야 한다:

- (A) 합친다 — 한 번의 저장 = 한 발, 본문에 예정·실적 변경을 함께 담는다. **우선 검토**
- (B) 유지한다 — 예정 변경은 "출근 안내", 실적 변경은 "정산 근거"라 성격이 다르다

### 5-3. 컴포넌트 분해는 선택이 아니라 전제

`EditSlotSheet` 557줄 + `WorkTimeEditor` 514줄. 합치면 800줄 상한을 확정적으로 넘는다. P1은 **다음 분해를 포함한 범위**다:

- `WorkTimeFields` — 예정/출근/퇴근 3필드 + [예정대로 기록] + 상태 배지
- `SlotRoleChips` — 역할 칩(마감 비활성 포함)
- `SlotColorChips` — 구분 색 팔레트
- 시트 본체는 조립과 저장 payload 구성만

### 5-4. 주의사항

- **P0-b의 하위호환은 협상 대상이 아니다.** 신 RPC가 prod에 적용된 시점부터 P3 배포 전까지 구클라가 기존 패치를 계속 보낸다. 새 키가 없을 때의 동작이 지금과 100% 같아야 한다.
- **역할 정원 거부를 추가하면 구클라가 막힌다.** 구클라 근무표는 마감 역할 칩을 비활성화하지 않으므로, 지금까지 통과하던 요청이 P0 이후 거부된다. → 에러 매핑(`utils/supabase.ts`)에 "정원이 찼어요" 분기를 P0와 **같은 배포**에 넣거나, P0에서는 `RAISE LOG` 관측만 하고 거부는 P3 이후로 미룬다. **후자를 권장** — 실제 충돌 빈도를 먼저 재는 게 낫다. ⚠️ 다만 메모리 기록상 prod 트래픽이 매우 작아(`work_logs 3건`, 2026-08-06 기록) **"기다려서 로그를 쌓는" 방식은 성립하지 않는다** — 관측 기간이 아니라 관계자 기기 직접 검증으로 판정할 것.
- **`modification_history` 이관은 Lost Update 경로다.** jsonb append를 클라에서 서버로 옮기는 것이므로 `FOR UPDATE` 잠금 안에서 읽고 써야 한다(메모리에 정산 이력 jsonb Lost Update 2경로가 미해결로 기록돼 있음 — 같은 함정).
- **pgTAP 선점검.** 트리거·쓰기 채널을 바꾸므로 착수 전 `supabase/tests/` 전수 grep (메모리 #420 교훈 — 트리거로 쓰기 채널을 좁혔다가 기존 pgTAP가 깨진 이력).
- **e2e 별도 확인.** `eslint.config.js` ignores에 `e2e/`가 있어 `npm run quality` 범위 밖이다. 시트 구조·라벨 변경 시 `e2e/` 별도 Grep 필수.

## 6. 미결 사항 (구현 착수 전 판단)

1. **역할 정원 거부 시점.** P0-b 즉시 거부 vs P3 이후 거부 (§5-4 주의사항 참조). 권장은 후자.
2. **`RoleChangeModal` 폐기 시 정원 정보 공급.** `filledByRole`은 `aggregateRoleFilledFromSubmap` 결과를 정산 화면이 계산해 주입한다. 통합 시트가 3곳에서 열리는데 각 진입점이 이 값을 어떻게 공급할지 정해야 한다. **서버 거부만 두고 클라 비활성을 포기하는 선택지도 유효**하다(정원 초과 시도가 드물다면 UX 비용 대비 이득이 작다).
3. **`WorkTimeEditor` 개조 vs 신규.** 현행 파일은 익일 판정·12시간 경고·`endTimeForSave` 보정 등 검증된 로직이 많아 **개조를 권장**. §5-3 분해가 전제.
4. **섹션 순서 — 시간순 vs 빈도순.** §8-1 참조. 사용자 확인 필요.

## 7. 범위 밖 (의도적 제외)

## 8. 사용자 마찰 검토 — 통합이 만드는 새 불편

통합은 "예측 가능성"을 얻는 대신 **창 하나가 길어진다**. 실제로 불편이 생길 지점을 짚는다.

### 8-1. 🔴 자주 쓰는 것이 아래에 있다 (섹션 순서)

| 축 | 언제 | 빈도 |
|---|---|---|
| 출근 예정 | 사전(D-7~전날) | **드묾** — 한 번 정하면 잘 안 바뀜 |
| 실제 출퇴근 | 당일·정산 전 | **잦음** — 홀덤펍 사장은 마감 후 거의 매일 정정 |

§3 화면 설계는 **시간순**(약속 → 실적)이라 논리적이지만, **빈도순과 반대**다. 매일 반복되는 동작이 스크롤 아래에 있으면 그 마찰이 매일 누적된다.

**대안 3안**

- (A) 시간순 유지 + 진입 맥락별 자동 스크롤 — 정산에서 열면 실적으로 스크롤. 구현이 눈에 띄고 "왜 중간부터 열리지" 혼란 여지
- (B) 실적을 위로 — 빈도는 해결되나 "약속 → 실적" 서사가 깨져 §3-1의 라벨 설명력이 사라짐
- (C) **예정 섹션 기본 접힘 + 한 줄 요약** — `출근 예정 18:00 · 딜러 ▸` 한 줄만 보이고 탭하면 펼침. 시간순도 지키고 실적이 첫 화면에 온다. **추천**

→ §6 미결 4.

### 8-2. 🟠 [예정대로 기록]을 못 찾으면 탭이 4배

버튼을 놓치면 사용자는 휠 피커를 열어 예정과 같은 시각을 직접 고른다 — 결과는 같지만 **탭 1회가 4~5회**가 된다.

**완화**: 별도 버튼에만 의존하지 말고 **출근 칸을 눌러 열리는 피커 상단에 `18:00 (예정)` 바로가기 칩**을 함께 둔다. 어느 쪽으로 접근해도 한 번에 끝난다.

### 8-3. 🟠 스태프 폰에 알림 2발

사장이 한 번 저장했는데 스태프에겐 "출근 예정 변경" + "근무 시간 변경" 2개가 간다(§5-2). **스태프는 사장보다 앱 관여도가 낮아 알림 피로가 이탈로 직결된다.** 통합 시트가 오히려 스태프 경험을 악화시키는 유일한 지점이므로 (A) 합치기를 우선한다.

### 8-4. 🟠 역할 마감 차단이 "고장"으로 느껴질 수 있다

지금 근무표에서는 마감 역할로도 옮길 수 있다(결함 ④). 이걸 막으면 **되던 게 안 되는** 변화다. 특히 대회 당일 급구 상황에서 "정원 초과인 걸 알지만 지금 넣어야 하는" 경우가 실재할 수 있다.

**두 선택지**

- (A) **강제 거부** — 정합성 우선. 사장은 공고에서 인원을 먼저 늘려야 함
- (B) **경고 후 허용** — 칩에 "(마감)" 표기 + 선택 시 확인 한 단계. 데이터는 정원 초과를 허용

⚠️ **어느 쪽이든 비활성만 두면 안 된다** — 왜 안 눌리는지 화면이 말해야 한다. 탭 시 `이 역할은 정원이 찼어요. 공고에서 인원을 늘려주세요.` 토스트를 최소 요건으로 한다. → 사용자 확인 필요.

### 8-5. 🟡 실수로 다른 축을 건드리면 함께 저장된다

지금은 화면이 나뉘어 있어 사고 범위가 좁았다. 한 시트가 되면 "퇴근만 고치려다 역할 칩을 스쳤는데 역할까지 바뀌는" 일이 가능하다.

**완화**: `EditSlotSheet`의 `resolveSlotTimePayload`(사용자가 안 건드린 축은 아예 전송하지 않음) 패턴을 **전 축으로 확장**한다. 이건 완화책이 아니라 **P1의 필수 요건**으로 둔다 — 역할 이력이 남는 축이라 오탐 저장이 이력을 오염시킨다.

### 8-6. 🟡 상태 배지 미리보기의 되돌림

저장하지 않고 닫으면 배지가 원래 상태로 돌아가야 한다. 시트 재오픈 시 잔존하면 "이미 출근 처리된 줄" 오해를 만든다. P1 구현 주의점.

### 8-7. 검토 결과 마찰이 **줄어드는** 지점

- 근무표에서 실적 편집 입구가 슬롯 종류에 따라 사라지던 문제 소멸(결함 ②)
- "이 화면에서 이건 못 고친다"를 배울 필요가 없어짐 — 4축은 어디서든 동일
- 색·메모가 보이는데 못 고치던 비대칭 해소
