## 0. 결론

**그리드는 아키텍처적으로는 잘 지어졌으나, UX 표면에서는 "구인구직 앱 옆에 세운 별관"이다.**

- **밑은 튼튼**: 쓰기 엔진은 기존 `add_direct_staff`·`work_logs`로 100% 수렴(중복 구현 0), 정산·QR·공고생성 전부 기존 경로 재사용, fail-closed 방어(RLS+RESTRICTIVE+앱 6곳), 코드↔마이그 드리프트 0, 플래그 우회 경로 0, 다크모드·a11y 견고.
- **표면에 구멍 2개(플래그 ON 차단급)**: ① **배치 슬롯 삭제 UI가 없다** — RPC(`remove_direct_staff`)는 있는데 화면에 빼는 버튼이 없음. ② **콜드스타트 막다른 길** — 첫 운영처 생성 직후 풀이 비어 전화번호 정확일치 검색 없이는 배치를 시작할 수 없음.
- **가장 큰 기회**: 그리드를 별동 도구가 아니라 **구인구직 수요 발생기(깔때기)** 로 연결하는 것. "부족 3명" 신호 → 프리필된 단발 공고 → 지원·확정 → E1 스팬으로 그리드에 자동 반영 — 이 루프의 후반부(확정→그리드 반영)는 이미 배선돼 있고, **전반부(부족→공고)가 껍데기만 있다**(venueId만 싣고 그리드 밖으로 방출).

### 2.3 3계층 개념 문제 (워크스페이스 → 운영처 → 공고)
- 첫 화면에서 사장이 만나는 개념: 워크스페이스 칩(2개 이상일 때) + 운영처 칩 + "+운영처 추가" — **가게 1개 사장에게 "운영처"는 워크스페이스와 구분 불가능한 동어반복**.
- 생성 UI(#221)의 존재 자체가 이 과잉의 비용: 운영처가 일급 개념이 아니었다면 생성 화면도, 그것이 누락됐던 출하차단 결함도 없었다.
- 스키마상 컨테이너는 불가피(§4.1)이므로 답은 제거가 아니라 **자동화**: 워크스페이스 생성/최초 그리드 진입 시 기본 운영처 자동 생성(`get_or_create_venue_container`가 이미 멱등이라 서버 변경 거의 불요) → 1:1:1 사장은 "운영처"라는 단어를 영영 안 봐도 됨. 다중 운영처(체인·대회사)만 선택기 노출. #221 생성 UI는 폐기가 아니라 고급 케이스 전용으로 강등.

## 3. 워크플로우 분석 — 기존 구인구직과의 관계

### 3.1 수렴돼 있는 것 (중복 아님 — 재설계 시 보존할 자산)
- **쓰기 엔진 단일**: 지원 확정(`confirm_application`)이든 직접배치(`add_direct_staff`)든 최종적으로 `work_logs` INSERT 한 길. 차이는 `application_id` NULL 여부뿐.
- **공고 생성**: 그리드 "공고 열기" = 기존 `my-postings/create` 라우트 재사용(신규 폼 없음).
- **정산·QR**: 그리드 전용 경로 없음. venue 스팬(`venue_span_posting_ids`)으로 조회만 확장, 정산 편집·QR 체크인은 기존 경로 합류.
- **그날 상세 뷰**: 기존 `ConfirmedStaffList` 재사용(`venueDayDetailMapping.ts`로 계약 맞춤).

### 3.2 진짜 중복 (통합 대상)
1. **[W-1] AddSlotSheet vs AddStaffModal 이중 UI** — 같은 훅(`useStaffPhoneSearch`)·같은 타입(`AddDirectStaffInput`)·같은 RPC(`add_direct_staff`)·후보행 렌더까지 사실상 복붙(`AddSlotSheet.tsx:454` 주석이 자인). 차이는 날짜 고정/선택과 풀 모드 유무뿐. **단일 컴포넌트(date·mode prop)로 통합 가능한 최대 중복.** 부수 결함: AddStaffModal 경로는 `weeklyGrid` 쿼리키 무효화를 안 해서 스태프탭에서 추가한 인원이 그리드에 늦게 반영될 수 있음(`useConfirmedStaff.ts:234-248`).
2. **[W-2] 같은 work_logs의 뷰 5개** — 그리드 월 캘린더 / 그리드 날짜 상세 / 내 공고 스태프탭 / 내 공고 정산탭 / 구직자 내 스케줄. 뷰 로직은 공유하므로 중복 구현이 아니라 **진입 화면 다중화** — 통합보다 네비게이션 정리(사장의 "인력" 허브 단일화) 대상.

### 3.3 단절 (구인구직 개선의 최대 기회)
그리드→구인구직 깔때기 루프:

```
[그리드] 부족 3명 신호 ──(F-4: venueId만 싣고 방출)──▶ [공고 작성 5섹션 수동 입력]
                                                            │
[그리드] 자동 반영 ◀──(E1 스팬: 이미 배선 완료 ✅)── [지원 → 확정(confirm_application)]
```

- **후반부는 완성**: venue_id 딸린 open 공고의 확정 인원이 `get_venue_grid_summary`/`get_venue_day_slots`에 자동 합산(E1 SSOT). 공고 뱃지(`+N`)도 셀에 표시됨.
- **전반부가 껍데기**: "부족 3명"을 아는 시스템이 공고 폼에 날짜·시간대·역할·모집인원을 하나도 안 실어줌. 사장은 50~80필드 폼(`JobPostingScrollForm`)을 처음부터 채워야 함. **부족 신호 → 원탭 "이 날짜에 3명 구인" 프리필 공고**가 되면: 단발 공고 생성 마찰 급감 → 공고 공급↑ → 구직자에게 일감↑ → 매칭 루프 가속. 그리드가 단골 관리 도구를 넘어 **마켓플레이스 수요 발생기**가 된다.
- 콜드스타트(F-2)와도 정렬: 풀이 빈 신규 사장의 자연스러운 첫 행동이 "공고로 사람 모으기"가 되도록 빈 풀 상태에서 공고 열기를 1순위 CTA로.

### 3.4 갭분석(2026-05-28)과의 관계
- 그리드가 **부분 우회 해결**: G6/Path5(일괄 승인 부재 — 풀 꽂기+지난주 복사로 승인 루프 자체를 생략), G4(단발 vs 반복 미분리 — 컨테이너 반복 배치로 대응).
- 그리드도 **그대로 앓는 것**: G2/F3 자정 넘는 시간대(F-8).
- 그리드 밖 잔존(구인구직 본체 개선 항목): 지역/거리 필터(1.1-Path1), 일자별 다른 시간대 UI(F2), 지원 충돌 감지(1.1-Path2).

## 4. 의존성 분석

### 4.1 DB 골격 (마이그 13종, 드리프트 0)
- 불변식: `work_logs.job_posting_id NOT NULL`(6테이블+5트리거 참조) → 컨테이너-as-공고는 자의적 과설계가 아니라 스키마 강제 최선(설계 v2 §2.2 대안 비교 참조).
- 앱이 호출하는 RPC 8종 전부 리포에 마이그 존재(`20260629000000`~`20260703000000`), 의존 헬퍼 5종 존재. **메모리 2건("PR #221 미머지", "staff_management_direct_add master 미반영")은 stale였고 2026-07-02/03 정정 완료.**
- 미검증 1건: prod 함수 본문 ↔ 리포 파일 byte-파리티(라이브 DB 실측 필요 — prod 우회 금지 가드로 이번 범위 밖).

### 4.2 컨테이너 영구 세금 현황
- **방어 완비**: RLS `USING(status<>'container')`(`20260630000400`) + RESTRICTIVE 직접쓰기 차단(`...500`) + CHECK + 앱 레포 6곳 `.neq('status', CONTAINER)`(`JobPostingRepository.ts:84,111,148,186,216,244`).
- **간극 3건**:
  1. [LOW-MED] 통계 RPC 2종(`get_job_posting_stats`, `get_regular_posting_date_counts`)이 컨테이너 **명시 배제가 아니라 status allow-list에 우연히 의존** — allow-list 완화 시 owner 통계로 leak. `statusValues.ts:47` "중앙 deny" 주석과 구현 사이 간극.
  2. [LOW] `loadJobPostingForVerify`(`JobPostingRepositoryHelpers.ts:76`)만 carve-out 누락(getById와 비대칭). DB RESTRICTIVE가 실피해는 막지만 일관성 결함.
  3. [LOW] 알림 딥링크↔플래그 시점 결합 — 플래그 OFF 롤백 시 잔존 배치알림 탭이 workspace로 바운스(`weekly-grid.tsx:171` Redirect).
- 이 세금 목록 자체가 재설계 논의의 정량 근거: **"컨테이너 모델의 유지비 = 방어 지점 9곳 + 잠복 결합 2곳"**.

### 4.3 플래그·결합도
- `weekly_grid_enabled`: 원격(app_config)+빌드타임 fallback, 게이트 4중(진입 버튼/화면 Redirect/쿼리 enabled/셀 그리드모드). **우회 경로 없음** → 재설계하더라도 휴면 상태 유지 비용 낮음.
- 역참조(기존→그리드)는 타입+위임+플래그 훅뿐 — 기존 런타임이 그리드에 의존하는 곳 없음 → **부분/전면 재설계의 blast radius 작음.**

## 5. 대회사 갭

- 코드상 이벤트/대회 모델 **전무**: `kind='dated'` 고정 생성(`VenueCreateSheet`), +7일 주간 복사(`copyLastWeek.ts:22`), 날짜별 soft target — 전부 **주 단위 반복 운영 전제**. D-7~D-day 수렴형(이벤트 스팬·카운트다운) 개념 없음.
- 별도 출하 중인 T-HOLDEM ops(대회 운영툴 1a~1d)와 **배선 0** — "대회사 인력 배치가 그리드 소속인가 ops 소속인가"의 제품 경계가 미정의. 재설계 세션에서 이 경계부터 정해야 그리드 스코프가 확정된다(권고: 그리드=홀덤펍 상시 배치에 집중, 대회 인력은 이벤트 모델로 별도 설계 후 ops와 접점 검토).
