# 운영 과금 설계 (2026-07-27, rev.2)

> **확정**: 구인구직 = 영구 무료. 매칭 영역 과금은 **긴급공고 1건뿐**.
> **설계 목표**: 요금 안내를 스크롤 없이 이해할 것. 요금제 비교표가 필요하면 실패한 설계다.
> 시장·경쟁 배경은 `2026-07-27-revenue-model-rebuild.md` 참조 (요금 구조는 이 문서가 최신).

## 1. 요금표

| 무엇을 | 얼마 |
|---|---|
| **구인구직** — 공고·지원자 관리·확정·리뷰·게시판 | **무료** (영구, 무제한) |

## 2. 가격 결정의 근거와 쟁점

### 2.1 긴급공고 5,000원 — 채택

10,000원 → 5,000원 인하에 동의한다.

- 1만 원은 "결제 결정"이지만 5천 원은 "그냥 누름"이다. 딜러 시급의 1/3 수준이라 비교 자체가 안 된다
- 미충원 자동 환불과 결합하면 **실질 리스크 0** → 첫 구매 전환율이 크게 오른다
- 매출은 볼륨이 2배가 되면 동일하고, 그 사이 쌓이는 사용 습관·데이터는 더 많다
- PG 수수료(건당 약 150~200원, 3~4%)를 감안해도 마진은 유지된다

**단, 묶음 할인(10건 40,000원)은 만들지 않는다** — 잔액 개념이 생기는 순간 크레딧이고, §8에서 기각한 항목이다.

### 2.2 대회 운영 30,000원 — 금액 채택, **형태는 건당으로**

금액은 그대로 쓰되 **월 구독이 아니라 대회 1건당**으로 간다. 이유:

| 월 구독의 문제 | 건당의 이점 |
|---|---|
| 대회사 수요는 **간헐적·시즌성**(D-7~D-day 집중). 안 여는 달엔 즉시 해지 압력 | 열 때만 낸다. 안 열면 0원 |
| 이탈률이 높아 구독의 유일한 장점(예측 가능성)이 사라진다 | **해지라는 개념 자체가 없다** → 이탈률 관리 불필요 |
| 갱신·유예·해지·재개 로직을 전부 만들어야 한다 | `purchases` 한 행이면 끝 |
| 월 3만 × 40곳 = 120만 원. 그 관리비용을 정당화 못 한다 | 월 30건 × 3만 = 90만 원, 관리비용 0 |

대회 1건 총예산(장소·상금·인력) 대비 3만 원은 부담이 아니고, "이번 대회 운영비 3만 원"이 "매달 3만 원씩 빠져나감"보다 훨씬 팔기 쉽다.

### 2.3 매장 운영 무료 — **되돌릴 수 없는 결정이라 형태를 바꿔 제안**

의도(초기 채택 극대화)에는 100% 동의한다. 다만 **"무료"로 확정하지 말고 "정가 5만 원 + 기간 한정 프로모션 무료"로 걸자**는 것이 제안이다. 사용자가 체감하는 것은 똑같이 0원이다.

**이유 1 — 비대칭성.** 유료를 무료로 푸는 건 언제든 가능하지만, **무료를 유료로 바꾸는 건 거의 불가능**하다. 지금 "무료 기능"으로 각인시키면 사실상 영구 무료가 확정된다. 되돌릴 수 있는 쪽을 선택하는 게 맞다.

**이유 2 — 현금화 상류가 법적으로 막혀 있다.** 무료 전략은 보통 "네트워크를 잠근 뒤 더 큰 결제 흐름을 먹는다"를 전제한다. 그런데 이 시장에서 그 큰 흐름(바이인·상금·참가권)은 관광진흥법상 진입 불가다. **하류가 막힌 시장에서 상류를 무료로 뿌리면 현금화 경로가 아예 없다.**

**이유 3 — 원가가 사용량에 비례한다.** QR 근태·정산은 DB 쓰기·연산·저장이 매일 누적된다. 무료 사용자가 늘수록 Supabase 비용이 선형으로 오른다. 매출이 붙지 않는 기능이 원가를 만든다.

**이유 4 — 지불의사가 가장 높은 자산을 버리게 된다.** 매장 운영은 (a) 대체재 없음 (b) 매일 씀 (c) 사업자가 지불 (d) 데이터 락인 강함 — 네 조건을 모두 만족하는 교과서적 과금 대상이다. 이걸 빼면 남는 건 전부 지불의사가 약한 항목들이다.

**제안 형태:**

```
매장 운영    월 50,000원
             └ 런칭 프로모션: 2027-12-31까지 전액 무료
             └ 프로모션 기간 가입 매장은 이후 평생 월 25,000원 (반값 고정)
```

- 체감은 무료와 동일 → 초기 채택 극대화 목표 그대로 달성
- **"지금 가입하면 평생 반값"이 오히려 강력한 가입 유인**이 된다
- 유료화 시점에 배신감이 없다(처음부터 공지된 프로모션)
- 시장 반응이 좋으면 프로모션을 연장하면 되고, 나쁘면 유지하면 된다 — **선택지가 보존된다**

> 그래도 완전 무료로 가시겠다면 그 판단을 따르겠습니다. 다만 그 경우 매장(홀덤펍)에서 나오는 매출이 긴급공고 5천 원뿐이라 **매장 ARPU가 월 1만 원 수준**이 되고, §4의 보완 수단이 선택이 아니라 필수가 됩니다.

## 3. 광고 — 형태를 구분해야 한다

"광고"에는 정반대 성격의 두 가지가 있고, 하나는 채택 다른 하나는 기각이다.

### ❌ CPM 네트워크 광고 (애드몹 등) — 기각

| 문제 | 내용 |
|---|---|
| 금액이 무의미 | 홀덤 인력 시장 MAU 상한은 수천 명. MAU 5,000 기준 월 **50~100만 원** 수준. 매장 운영 구독 200곳(1,000만 원)과 자릿수가 다르다 |
| 공급측을 깎는다 | 구직자(딜러) 화면에 광고를 붙이면 이 마켓플레이스의 생명인 **공급 유동성**이 훼손된다 |
| 브랜드 훼손 | 사업자 대상 B2B 서비스에 도박·대출 광고가 자동 노출되면 최악이다. 광고 소재 통제가 불가능하다 |

### ✅ 직접 판매 스폰서 슬롯 — 채택

같은 "광고"지만 CPM이 아니라 **월정액 직접 판매**다. 단가가 자릿수 다르고 소재를 완전히 통제한다.

| 인벤토리 | 근거 | 특징 |
|---|---|---|
| **전광판 하단 스폰서** | `app/(public)/monitor/[token].tsx` | 대회장 **대형 스크린** 노출. 관중=홀덤 소비자라 타겟 완벽. "대회 1건당 노출 패키지"로도 판매 가능 |
| 공고 목록 상단 | `app/(public)/jobs/index.tsx` (비로그인 접근) | 구인자·구직자 동시 노출 |
| 게시판 상단 | `board` 5종 | 커뮤니티 체류 시간 활용 |
| 대회 캘린더 (후행) | 플레이어 포털 확장 시 | |

**광고주 후보**: 딜러 아카데미, 홀덤 용품(칩·테이블·셔플머신), 대회 홍보, 홀덤펍 창업·POS, 주류 유통

**단가**: 슬롯당 월 300,000~500,000원 × 3~5슬롯 = **월 100~250만 원**

**원칙 3가지**
1. 슬롯 수 상한을 고정한다(최대 5개). 늘리면 지면이 지저분해지고 단가가 떨어진다
2. 광고주 심사 — 도박·대출·불법 업소 광고는 받지 않는다
3. **구직자 전용 화면(지원 흐름·근무 일정)에는 넣지 않는다.** 공급측 경험은 건드리지 않는다

## 4. 보완 수익원 — 매장 매출 공백 메우기

매장 운영을 무료(또는 프로모션 무료)로 두는 동안, 매장에서 나오는 매출은 긴급공고뿐이다. 이를 메울 후보를 지불 주체 기준으로 정리한다. **구직자 과금은 전부 배제**(규제 + 공급 유동성).

| # | 상품 | 지불 주체 | 가격 | 평가 |
|---|---|---|---|---|
| 1 | **스카우트** — 인증 딜러 인재풀 열람 + 먼저 제안 보내기 | 구인자 | 건당 3,000원 | ⭐ 최우선. `bubble_score`·근무 이력이 이미 있어 구현 부담 적음. 매장 ARPU 직접 보강 |
| 2 | **스폰서 슬롯** (§3) | 광고주 | 월 30~50만 | ⭐ 대회 규모 확보와 함께 |
| 3 | **딜러 아카데미 제휴** — 신규 딜러 교육 연결, 수강 성사 수수료 | 교육기관 | 성사당 or 월정액 | ⭐ **공급 확대와 매출이 동시에 발생**. 구직자가 아닌 기관이 지불하므로 규제 문제 없음 |
| 4 | 대회 홍보 등록 — 전국 대회 캘린더 노출 | 대회사 | 건당 | 🟡 플레이어 포털 이후 |
| 5 | 임금 시세 리포트 | B2B | — | 🟡 초기엔 무료 공개로 유입·권위 확보 |

**3번(아카데미 제휴)이 특히 좋다.** 홀덤펍의 근본 문제는 "딜러가 없다"이고, 아카데미는 "수강생을 취업시켜야 한다"이다. UNIQN이 그 사이에 서면 양쪽 모두에게 가치가 있고, 신규 딜러 유입은 곧 마켓플레이스 공급 확대다. 매출과 제품이 같은 방향으로 움직이는 몇 안 되는 상품이다.

## 5. 단순함을 만드는 규칙 4개

| # | 규칙 | 버리는 것 |
|---|---|---|
| 1 | **요금제는 1개다.** 매장 운영은 켜거나 끈다 | Free/Pro/Business 비교표 |
| 2 | **한도가 없다.** 무제한이므로 셀 필요가 없다 | "월 30건까지 무료" · 초과 UI · 카운터 테이블 · 월초 리셋 크론 |
| 3 | **단위는 눈에 보이는 것으로.** 매장 1곳/월, 대회 1건, 공고 1건 | 좌석·크레딧 등 추상 단위 |
| 4 | **처음은 무료.** 대회 첫 1건, 매장은 프로모션 기간 전체 | 체험 자격 심사 |

> 규칙 2가 가장 중요하다. **한도가 복잡함의 근원**이다. 없애는 순간 사용량 집계·초과 판정·잔여량 표시·월초 리셋·초과 청구가 전부 사라진다.

## 6. 무료 / 유료 경계

> **"사람 구하는 건 공짜, 사람 굴리는 건 유료."**

| 무료 (영구) | 매장 운영 | 대회 건당 |
|---|---|---|
| 공고 등록·수정·마감 | QR 출퇴근 체크인 | 대회 생성·복제 |
| 지원자 조회·확정·취소 처리 | 근무시간 수정 | 등록데스크·체크인 |
| 리뷰 작성·평판 조회 | 정산 계산·확정 | 테이블/좌석 배정·리드로 |
| 게시판·알림·프로필 | 지점 월정산·역할별 단가표 | 블라인드 클럭 |
| 워크스페이스·협업자 (인원 무제한) | 주간 근무표 편집·직접 배치 | 전광판·플레이어뷰 |
| 대회 **공고** 등록 | 정산 내보내기 | 상금·바운티 계산 |

### 6.1 잠겨도 데이터는 인질이 아니다

| 미결제 시 | 동작 |
|---|---|
| 새 QR 체크인 / 정산 확정 / 근무표 편집 | ❌ 잠금 |
| 지점 월정산 **집계 산출** | ❌ 잠금 |
| 과거 근무 기록·정산 내역 **열람** | ✅ 항상 열림 |
| 내 데이터 내보내기 (`settings/my-data`) | ✅ 항상 열림 |
| 구인구직 전체 | ✅ 정상 작동 |

정산 데이터를 볼모로 잡는 순간 신뢰가 무너진다. 잠금은 "앞으로 못 쓴다"이지 "지난 걸 뺏는다"가 아니다.

## 7. 생명주기

상태는 4개, 판정은 **컬럼 하나**로 한다.

```
[운영 기능 첫 사용]
      ↓ 자동 시작 (아무것도 묻지 않음)
   trialing  ──→  [만료 D-7 / D-3 / D-1 알림]
      ↓ 결제                    ↓ 미결제
   active                    past_due (7일 유예, 기능 그대로)
      ↑                          ↓
      └────── 결제 즉시 해제 ──── locked
```

- **판정식은 `valid_until > now()` 하나뿐.** 유예기간은 상태 분기가 아니라 `valid_until`에 +7일을 반영해 처리 → 코드에 `if (status === 'past_due')` 분기가 존재하지 않는다
- `status`는 **화면 표시 전용**. 권한 판정에 쓰지 않는다
- **런칭 프로모션 기간에는 `valid_until`을 프로모션 종료일로 넣기만 하면 된다** — 별도 무료 로직이 필요 없다. 이것이 "정가 + 프로모션" 형태를 권하는 실무적 이유이기도 하다
- 대회 패스는 생명주기가 없다. 결제했으면 그 대회는 영구히 열린다

## 8. 데이터 모델 — 테이블 2개, 함수 2개

```sql
-- ① 매장 운영 구독: 워크스페이스당 0 또는 1행
create table public.workspace_subscriptions (
  workspace_id uuid primary key references public.workspaces(id) on delete cascade,
  status       text not null check (status in ('trialing','active','past_due','locked','canceled')),
  valid_until  timestamptz not null,        -- ★ 권한 판정의 유일한 근거
  price_krw    integer not null default 50000, -- 얼리버드 반값(25000) 고정용
  billing_key  text,                        -- PortOne 빌링키
  started_at   timestamptz not null default now(),
  updated_at   timestamptz not null default now()
);

-- ② 단건 결제: 긴급공고 · 대회 (영수증 겸 이용권)
create table public.purchases (
  id           uuid primary key default gen_random_uuid(),
  workspace_id uuid not null references public.workspaces(id),
  kind         text not null check (kind in ('urgent_posting','tournament')),
  target_id    uuid not null,               -- job_postings.id | ops_tournaments.id
  amount_krw   integer not null,            -- 0 = 무료 제공분
  status       text not null check (status in ('paid','refunded')),
  paid_at      timestamptz not null default now(),
  unique (kind, target_id)                  -- 같은 대상 중복 결제 불가
);
```

```sql
create function public.has_operations(p_workspace uuid) returns boolean
  language sql stable security definer set search_path = public, pg_temp as $$
  select exists (
    select 1 from public.workspace_subscriptions
    where workspace_id = p_workspace and valid_until > now()
  );
$$;

create function public.is_purchased(p_kind text, p_target uuid) returns boolean
  language sql stable security definer set search_path = public, pg_temp as $$
  select exists (
    select 1 from public.purchases
    where kind = p_kind and target_id = p_target and status = 'paid'
  );
$$;
```

**요금제 테이블은 만들지 않는다.** 가격은 `app_config` 값 3개(`price.operations_monthly`, `price.urgent_posting`, `price.tournament`)면 충분하다.

**과금 주체는 `workspace`.** `job_postings.workspace_id`가 이미 NOT NULL이라 경계가 스키마상 확정돼 있다.

## 9. 게이트를 걸 지점 (실제 코드 위치)

쓰기는 전부 SECDEF RPC 경유이므로, RPC 진입부에 검사 한 줄 추가로 끝난다.

### 매장 운영 (`has_operations(workspace_id)`)

| 대상 | 지점 |
|---|---|
| QR 출퇴근 | `process_qr_checkin_atomically` |
| 근무표 직접 배치 | `add_direct_staff` · `remove_direct_staff` · `set_venue_soft_target` |
| 역할별 단가표 | `set_venue_role_salary` |
| 지점 월정산 산출 | `get_venue_grid_summary` · `get_venue_day_slots` |
| 정산 확정·시간 수정 | `src/services/work/settlement/settlementMutation.ts` — `updateSettlementStatus` / `updateWorkTimeForSettlement` / `updateWorkLogCustomSettlement` 대응 쓰기 경로 |

### 긴급공고 (`is_purchased('urgent_posting', posting_id)`)

- 지점: 공고 **발행 시점** (`src/repositories/supabase/JobPostingRepository.ts:616` insert 경로 — `posting_type='urgent'`)
- 흐름: 작성 → draft 저장(무료) → **발행 시 결제** → open. 결제 전 작성 내용은 draft로 보존
- **미충원 자동 환불**: 마감 시각까지 확정 인원 0명이면 `status='refunded'` + 환불

### 대회 운영 (`is_purchased('tournament', tournament_id)`)

- 지점: `ops_create_tournament` · `ops_duplicate_tournament`
- 대회 **공고**(스태프 모집)는 무료. 과금은 **운영 엔진을 켤 때**만
- 결제 실패 시 대회 행을 만들지 않는다(고아 데이터 방지)

### 검사 실패 시

`AppError` E6(비즈니스) 계열에 `PAYMENT_REQUIRED` 코드 1개 추가. 클라이언트는 이 코드를 받으면 결제 안내 시트를 띄운다. **화면마다 개별 분기하지 않는다.**

## 10. 결제 수단

- **PortOne 빌링키** — 본인인증으로 이미 연동된 벤더라 추가 통합 비용 최소
- 카드 1회 등록 → 매장 운영은 매월 자동 청구, 긴급공고·대회는 원클릭
- 세금계산서 자동 발행

**앱스토어 IAP**: 구인 광고·오프라인 인력 서비스 요금은 디지털 재화가 아니어서 IAP 대상으로 보기 어렵다(알바몬·잡코리아 앱은 앱 내 PG 결제 중). 다만 심사 판단이 갈릴 수 있으므로 — 1차는 웹 결제 + 앱은 상태 표시, 2차로 앱 내 PG 결제를 심사 문의 후 도입. 긴급공고는 "당장 사람 없는 순간"에 사는 상품이라 웹 이동 마찰이 전환율을 직접 깎는다.

## 12. 기존 사용자 이행 (v1.0.5 배포 중)

- 시행일에 **모든 기존 워크스페이스에 프로모션 종료일까지 `valid_until` 부여** (`status='trialing'`)

- 별도 예외·특례 없음

## 14. 매출 시나리오 비교 (24개월차 MRR)

매장 운영의 처리 방식이 결과를 가른다.

| 항목 | A. 매장 영구 무료 | B. 프로모션 후 유료 |
|---|---|---|
| 긴급공고 (5,000원 × 600건) | 300만 | 300만 |
| 매장 운영 | **0** | 얼리버드 120곳×25,000 + 신규 80곳×50,000 = **700만** |
| 대회 운영 (30,000원 × 30건) | 90만 | 90만 |
| 스폰서 슬롯 | 150만 | 150만 |
| 스카우트 | 100만 | 100만 |
| **MRR** | **약 640만 원** | **약 1,340만 원** |
| **ARR** | 약 7,700만 원 | 약 1.6억 원 |
| 고정비 500만/월 기준 마진 | 140만 (10개월 누적 1,400만) | 840만 |

- A안도 흑자는 난다. 다만 **1인 운영 유지 수준**이고 재투자 여력이 거의 없다
- 차이 700만 원의 전부가 "매장 운영을 무료로 확정하느냐"에서 나온다
- **A안을 택하더라도 §4의 보완 수익원(스카우트·아카데미·스폰서)은 선택이 아니라 필수**가 된다
