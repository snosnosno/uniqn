# 고정공고 2차 남은 작업

작성일: 2026-04-05  
상태: Proposed  
기준 코드: `uniqn-mobile/`, `firestore.rules`

## 1. 현재 기준선

현재 상태는 아래와 같다.

- 1차 필수 범위 완료
- 2차 선행 항목 `고정공고 편집 지원` 완료

따라서 이 문서는 `남아 있는 2차 작업`만 다룬다.

## 2. 2차 목표

2차의 핵심 목표는 `장기채용 후보 모집/확정` 상태에 머물러 있는 fixed를 실제 운영 가능한 고정 근무 플로우로 확장하는 것이다.

즉, 아래를 완성해야 한다.

- 반복 근무 패턴 정의
- 실근무일 생성
- WorkLog 연결
- QR 연결
- 정산 연결
- 취소/재배치/no-show 같은 후속 lifecycle 복원

## 3. 남은 작업 목록

### 3.1 운영 모델 완성

상태: Not started

- 반복 근무 패턴을 실제 운영 가능한 스케줄 모델로 확장
- fixed 확정 인원을 실근무일 단위로 생성
- 실근무일 기준으로 WorkLog 생성
- 실근무일 기준으로 QR 생성 범위 연결
- 실근무일 기준으로 정산 계산 연결
- 취소요청, 확정취소, 재배치, no-show 복원

### 3.2 내부 운영 보강

상태: Partial

완료:

- fixed 편집 지원

남은 작업:

- fixed 확정자 관리 화면을 장기근무 운영 중심으로 재구성
- 역할별 정원/충원/대기 상태를 더 명확하게 표시
- fixed 전용 상태 문구와 운영 문구 통일
- 재지원 정책 정의
- 역할 변경 정책 정의

### 3.3 외부 노출 확장

상태: Not started

- 공개 상세
- 공유 지원
- 검색 노출
- 공개 노출용 fixed 정렬/노출 정책 정의

기본 원칙:

- 앱 홈 `전체` 혼합 피드는 계속 분리 유지
- fixed는 필요 시 별도 노출 경로로 확장

## 4. 권장 구현 순서

### Step 1. fixed runtime model 정의

목표:

- 모집/확정 상태의 fixed와 실제 운영 중인 fixed를 구분할 수 있게 한다.

필요 작업:

- 실근무일 또는 runtime instance 개념 정의
- fixed 확정자와 runtime instance 연결 방식 설계
- runtime instance 상태 정의

권장 원칙:

- 기존 `jobPostings`와 `applications`를 유지하고 runtime 데이터만 분리
- dated의 `assignment/worklog` 의미를 fixed에 억지로 재사용하지 않기

### Step 2. 반복 패턴 -> 실근무일 생성

목표:

- fixed 공고의 반복 패턴이 실제 운영 가능한 날짜 목록으로 전개되게 한다.

필요 작업:

- 주 n회 패턴 해석 규칙 정의
- 시작일/생성 범위/미리 생성할 기간 정의
- 역할별 확정자를 실근무일에 배정하는 규칙 정의

결정 필요:

- 실근무일은 자동 생성인지 수동 생성인지
- 몇 주 단위로 미리 생성할지
- 역할별 인원 변경 시 기존 실근무일을 어떻게 보정할지

### Step 3. WorkLog / QR / Settlement 연결

목표:

- fixed도 dated와 동일한 운영 도구를 사용할 수 있게 한다.

필요 작업:

- runtime instance에서 WorkLog 생성
- QR 범위를 runtime instance 기준으로 생성
- 정산 조회/계산을 runtime instance와 WorkLog 기준으로 연결

주의:

- 1차 fixed confirmation은 WorkLog를 만들지 않는 계약을 유지해야 한다.
- WorkLog는 반드시 실근무일 생성 이후 단계에서만 만들어야 한다.

### Step 4. lifecycle 복원

목표:

- 운영 중 발생하는 예외 플로우를 fixed에서도 처리할 수 있게 한다.

필요 작업:

- 취소요청
- 확정취소
- 재배치
- no-show
- 운영 메모 / 처리 이력

주의:

- lifecycle은 runtime instance 기준으로 설계해야 한다.
- 현재 1차 application 중심 상태 전이만으로는 부족하다.

### Step 5. 내부 운영 UI 강화

목표:

- employer가 fixed 확정자와 실근무 운영 상태를 한 화면에서 관리할 수 있게 한다.

필요 작업:

- 확정자 목록
- 역할별 충원 현황
- 실근무일별 배정 현황
- 이탈/대기/교체 상태 표시

### Step 6. 공개 노출 확장

목표:

- 내부 운영 모델이 안정화된 후 외부 유입을 연다.

필요 작업:

- 공개 상세
- 공유 지원
- 검색 노출
- 공개 노출 정책 및 정렬 규칙

## 5. 유지해야 할 계약

2차가 완료되기 전까지 아래 계약은 유지한다.

- 공고당 지원 1건
- 지원당 역할 1개
- 확정당 역할 1개
- fixed confirmation 시 WorkLog 생성 없음
- fixed는 dated 예외가 아니라 별도 운영 플로우
- 앱 홈 `전체` 혼합 피드 미통합

## 6. 테스트 계획

### 6.1 2차 수용 테스트

- fixed 편집 후 역할/스케줄 반영 확인
- 반복 패턴에서 실근무일 생성 확인
- 실근무일 기준 WorkLog 생성 확인
- QR/정산 연결 확인
- 취소요청/확정취소/재배치/no-show 확인
- 공개 노출 후 내부/공개 회귀 확인

### 6.2 회귀 포인트

- regular/tournament/urgent 생성/지원/확정 회귀 없음
- fixed 1차 계약 유지
- rules / repository / UI gate 정합성 유지

## 7. 메모

- 다음 구현 우선순위는 `반복 패턴 -> 실근무일 생성 모델`이다.
- 공개 노출보다 운영 완성을 먼저 한다.
- 다중 역할 지원, 중복지원, mixed all-feed 통합은 당장 열지 않는다.
