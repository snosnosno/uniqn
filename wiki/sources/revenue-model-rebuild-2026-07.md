# 소스: 수익모델 원점 재분석 + 운영 과금 설계 (2026-07-27)

**두 문서 관계:** `revenue-model-rebuild` 가 시장·경쟁·단위경제 **배경 분석**이고, `operations-billing-design` 이 **확정 요금 구조**다. 요금 수치가 어긋나면 **후자가 최신**이다(전자 §5 요금표는 초안이며 문서 자체가 그렇게 명시한다).

방법론이 특이하다 — 기존 수익모델 문서와 지갑/IAP 이력을 **입력에서 배제**하고 코드에 실제 구현된 자산과 시장 구조만으로 원점 재분석했다. 폐기된 모델([[wallet-iap-removal]])의 전제가 결론을 오염시키는 것을 막기 위한 의도적 격리다.

## 핵심 판단 3개

1. **매칭에 과금하면 진다.** 대체재가 무료(게시판·카톡 오픈채팅)이고, 성사 수수료는 사용자를 앱 밖 직거래로 밀어내 **근태·정산 레이어까지 함께 잃는다**.
2. **운영 레이어는 과금해도 이긴다.** 대체 불가(게시판엔 없다) · 데이터가 쌓일수록 이탈 비용 증가(근무 이력·정산·평판) · 지불 주체가 사업자.
3. **TAM 이 작다**(홀덤펍 약 2,000개 추정). 그래서 전략축은 수수료율 최적화가 아니라 **매장당 ARPU 확대** — 단일 요금제가 아닌 스택 구조가 필연.

경계 한 줄: **"사람 구하는 건 공짜, 사람 굴리는 건 유료."** 기능 단위가 아니라 **목적 단위**로 그은 것이 요점이다 — 사용자가 외울 수 있어야 한다.

## 기각된 후보와 사유 (재론 방지)

| 후보 | 기각 사유 |
|---|---|
| 성사당 매칭 수수료 | 카톡 직거래 이탈 유발 → 운영 레이어까지 상실 · 무료 대체재로 가격 탄력성 높음 · 직업소개 요금 규제 접점 |
| 구직자(스태프) 과금 | 규제 리스크 + **공급측 유동성이 이 마켓의 병목** — 공급을 깎는 과금은 자해 |
| 바이인·상금 결제 수수료 | 관광진흥법 카지노 유사행위 리스크 — 한국 홀덤 맥락에서 가장 위험 ([[ops-no-money-flow]] 와 동일한 경계) |
| 앱 내 IAP | B2B 과금은 웹 결제로 → 스토어 수수료 30% 회피 |

## 설계 규칙 4개 — 복잡도 억제 장치

이후 모든 과금 기능 요청은 이 4개에 비춰 판단한다. 지키면 과금이 복잡해질 수 없다.

1. **요금제는 1개다** — 매장 운영은 켜거나 끈다 (Free/Pro/Business 3단 비교표 폐기)
2. **한도가 없다** — 무제한이므로 사용량을 셀 필요가 없다
3. **단위는 눈에 보이는 것으로** — 매장 1곳/월, 대회 1건, 긴급공고 1건 (좌석·건수·용량 등 추상 단위 폐기)
4. **처음은 무료** — 매장 30일, 대회 1건

> 규칙 2 가 가장 중요하다. **한도가 복잡함의 근원**이다. 한도를 없애는 순간 사용량 집계·초과 판정·잔여량 UI·월초 리셋 크론·초과분 청구가 **전부 사라진다**. 대신 가격을 한도 없는 값으로 잡는다(월 5만 원 = 딜러 4시간 인건비 — 한도로 아낄 금액이 아니다).

이 규칙 때문에 rebuild 초안의 무료 사용량 한도(월 30건)·좌석 추가 과금·크레딧 묶음·다지점 할인이 **전부 폐기**됐다. 초안 대비 가격도 조정됐다(Pro 59,000 → 매장 운영 50,000 / 부스트 9,900 → 긴급공고 10,000 / 대회 99,000 → 100,000).

## 코드가 이미 갖고 있는 훅

기능 문서가 아니라 스키마·라우트에서 직접 확인된 것만: 공고 유형 4종에 **`urgent` 와 `urgent_config` jsonb 가 이미 스키마·zod 양쪽에 존재**한다(`uniqn-mobile/src/schemas/jobPosting.schema.ts:368`, baseline 마이그 `:254-259`). 긴급 상품은 데이터 훅이 완비돼 있어 신규 스키마 없이 착수 가능하다는 뜻이다.

과금 주체 경계는 `workspace` 로 **스키마상 이미 확정**돼 있다.

## 미결 / 주의

- 이 두 문서는 **분석·설계이며 구현이 아니다.** 코드 변경 0줄로 머지됐다(PR#361). 엔타이틀먼트 검사·웹 결제·과금 UI 는 전부 미착수.
- 기존 사용자 **grandfathering** 이 전제다 — v1.0.5 가 이미 배포 중이므로 "이미 무료로 쓰던 기능을 뺏지 않는다".
- 대회 운영 과금은 [[ops-no-money-flow]] 경계를 침범하지 않는다: 과금 대상은 **운영 툴 이용권**이지 바이인·상금 흐름이 아니다. 이 구분이 흐려지는 순간 규제 리스크가 살아난다.
