# 결정: 조회 실패와 빈 상태는 절대 같은 화면을 쓰지 않는다

## 결론

**실패를 빈 배열로 렌더링하면 화면은 성공을 가장한 안내를 띄운다.** 8개 화면이
"모든 평가를 완료했어요" · "신청 내역이 없습니다" 를 조회가 **실패했을 때** 보여주고 있었다(PR#434).
빈 상태 문구는 대개 긍정형이라, 실패했을 때 나오면 단순한 오표시가 아니라 **거짓 안심**이 된다.

## 왜 위험한가 — 두 사례 (코드로 검증됨)

**리뷰 허브** (`app/(app)/reviews/history.tsx`): 7일 마감이 걸린 기능인데 조회 실패가
"모든 평가를 완료했어요"로 나온다. 이 안내를 믿고 화면을 닫으면 **평가 기회가 실제로 소멸한다.**
빈 상태가 사용자에게 "더 할 일 없음"이라는 **행동 지시**로 읽히는 구조에서 특히 치명적이다.

**구인자 신청 현황**: 실패가 `!application` 분기로 떨어져 "내역 없음 → 신청하기"를 띄운다.
심사 중인 사용자가 **중복 신청**을 하게 된다. 실패를 "없음"으로 접으면
사용자는 없어진 것을 **다시 만들려고** 한다 — 무해한 오표시가 아니라 쓰기 사고를 유발한다.

## 근본 원인은 화면이 아니라 훅이었다

`usePendingReviews` 는 내부적으로 `useQuery` 4개를 쓰면서 **`error`·`refetch` 를 반환조차 하지 않았다**.
화면에 분기 로직이 없던 게 아니라, **분기할 재료가 없었다.**

> 🔑 실패 표시가 없는 화면을 만나면 화면을 고치기 전에 **훅이 실패를 위로 올릴 수 있는지** 먼저 보라.
> 훅이 error 를 삼키면 그 훅을 쓰는 모든 화면이 같은 결함을 물려받는다 — 개별 화면 수정은 두더지잡기가 된다.

합성할 때 주의: 구인자 전용 쿼리의 error 는 `isEmployerReviewer` 일 때만 반영한다.
**`enabled` 조건과 error 합성 조건이 대칭이어야** 한다. 비대칭이면 돌지도 않은 쿼리의
`error` 를 읽어 항상 실패로 보이거나, 반대로 진짜 실패가 묻힌다.

## 에러 상태는 지워질 수 있어야 한다

`useJobDetail` 은 realtime 구독 에러가 **성공 갱신에도 `refresh()` 에도 지워지지 않아**,
캐시된 공고 위에 영구 에러 화면을 씌우고 있었다. '다시 시도' 버튼이 눌러도 아무 일이 없는 —
즉 **버튼이 거짓말을 하는** 상태다.

> 🔑 에러 상태를 세우는 경로가 있으면 **지우는 경로**도 같은 수만큼 있어야 한다.
> 지속 실패는 `onError` 가 다시 세우므로, 낙관적으로 지워도 안전하다.

## 규율

1. 목록 화면의 상태는 **로딩 / 실패 / 빈 / 데이터 4가지**다. 실패와 빈을 하나로 합치지 않는다.
2. 빈 상태 문구가 **완료·성공·안심**을 뜻한다면(“모두 완료”·“내역 없음”) 실패 분기는 필수다.
3. 실패 화면에는 **재시도**가 있어야 하고, 재시도가 실제로 상태를 되돌릴 수 있어야 한다.
4. 훅은 `error` 와 `refetch` 를 반환한다. 여러 쿼리를 합성하는 훅은 그 둘도 합성한다.
